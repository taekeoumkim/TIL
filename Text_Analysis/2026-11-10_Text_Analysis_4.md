# TIL | 2026-11-10 — 유사 문서 검색과 RAG의 검색 품질

지난 학습에서 코사인 유사도로 벡터를 비교하는 방법을 배웠다. 오늘은 정제한 명언 데이터를 검색 대상으로 준비하고, 높은 순위의 결과가 실제로 질문의 의도에 맞는지 확인하는 과정을 학습했다.

## 1. 검색할 문서와 임베딩 준비

`quotes_clean.csv`의 한 행을 검색 문서 하나로 삼는다. `text`를 임베딩 모델에 입력하고, 벡터와 원본 행을 고유한 `document_id`로 연결한다. 검색 결과에서 ID를 조회하면 명언 본문과 작성자, 태그, 출처를 함께 확인할 수 있다.

| 항목 | 역할 |
| --- | --- |
| `document_id` | 벡터와 원본 행을 연결하는 식별자 |
| `text` | 임베딩을 생성할 명언 본문 |
| `author`, `tags`, `source_url` | 작성자, 주제, 출처를 확인하는 메타데이터 |
| 문서 임베딩 | 본문의 의미적 특징을 담은 검색용 벡터 |

| 구분 | 생성 시점 | 관리 방법 |
| --- | --- | --- |
| 문서 임베딩 | 검색 자료를 준비할 때 | 저장해 재사용하고 본문이 바뀌면 해당 벡터를 갱신한다. |
| 질문 임베딩 | 사용자가 검색을 요청할 때 | 새 질문을 벡터로 바꿔 저장된 문서 벡터와 비교한다. |

질문과 문서의 벡터는 같은 공간에서 비교할 수 있어야 한다. 임베딩 모델을 바꾸면 기존 벡터와의 호환성을 확인하고 필요하면 문서 벡터도 새 모델로 다시 생성한다. 한국어 질문으로 영어 명언을 검색할 때는 두 언어 사이의 검색을 지원하는 모델인지 확인한다.

```text
문서 준비 → 본문 벡터화 → 문서 ID와 함께 저장
검색 요청 → 질문 벡터화 → 코사인 유사도 계산 → Top-K 후보 → 원문 조회
```

## 2. 검색 점수와 Top-K 결과 해석

코사인 유사도 0.86은 질문과 문서 벡터의 방향이 얼마나 비슷한지를 나타내는 점수다. 정답 확률로 환산할 수 없으며, 점수 분포는 모델과 문서 집합에 따라 달라진다. 검색 순위는 후보끼리 비교하는 데 쓰고, 실제 관련성은 질문과 원문을 대조해 판단한다.

실패 후 다시 도전할 수 있도록 격려하는 명언을 찾는 상황을 가정했다. 아래 문장과 점수는 학습자료의 설명용 예시다.

| 순위 | 검색된 문장 | 유사도 | 적합성 판단 |
| --- | --- | ---: | --- |
| 1 | Failure means you should stop trying. | 0.89 | 실패를 다루지만 도전을 멈추라는 내용이다. |
| 2 | Every setback is a chance to try again. | 0.82 | 실패를 다시 도전할 기회로 보므로 요청에 부합한다. |
| 3 | Small progress is still progress. | 0.74 | 격려의 메시지가 있지만 실패 이후의 재도전을 직접 다루지는 않는다. |

Top-K에서 `K`는 검토할 후보 수다. `K`를 늘리면 상위권에서 밀린 관련 문서를 찾을 수 있지만, 관련성이 낮은 문서까지 검토해야 한다. 최종 결과가 두 개 필요하다면 후보를 세 개나 다섯 개까지 조회한 뒤 원문을 확인해 선택할 수 있다. 반환 결과에는 문서 ID와 점수 외에도 본문, 작성자, 출처를 포함해 선택 근거를 확인할 수 있게 한다.

## 3. 검색 결과의 적합성 검증

| 확인 항목 | 판단 기준 |
| --- | --- |
| 주제 관련성 | 문서가 질문과 관련된 주제를 다루는가? |
| 조건 충족 | 미완료, 지연, 재도전처럼 질문이 요구한 조건을 충족하는가? |
| 정보 충분성 | 필요한 내용을 제공하거나 답변에 필요한 사실을 뒷받침하는가? |

검증용 질문과 관련 문서 ID 또는 판정 기준을 미리 기록한 뒤 실제 상위 결과와 비교한다. 예를 들어 환불 지연 사례를 검색할 때는 환불 미완료·지연 사례를 적합한 결과로 정한다. 상위 결과에 환불 완료 사례가 들어오면 주제는 맞지만 상태 조건에서 실패한 것이다. 여러 유형의 질문으로 기대한 문서가 포함되는지와 상위에 부적합한 문서가 얼마나 섞이는지를 살핀다.

| 증상 | 확인할 부분 |
| --- | --- |
| 필요한 문서가 검색되지 않음 | 원본 데이터에 해당 문서가 있는지 |
| 관련 문서가 후보 밖으로 밀림 | 검색 순위와 `K` 설정 |
| 관련 없는 문서가 상위에 반복해서 나타남 | 임베딩 모델이 데이터와 질문에 적합한지 |
| 한국어 질문에 영어 문서 검색이 잘 되지 않음 | 모델의 언어 간 검색 지원 여부 |
| 검색 결과와 원문이 어긋남 | 문서 ID 연결과 본문 수정 후 벡터 갱신 여부 |

## 4. 검색 결과를 RAG의 답변 근거로 연결

RAG(Retrieval-Augmented Generation)는 질문과 관련된 외부 문서를 찾아 LLM의 입력에 포함하고, 그 내용을 바탕으로 답변을 생성하는 방식이다. 명언 추천이라면 관련 명언의 본문·작성자·출처를 전달해 추천 이유를 설명하게 할 수 있다.

```text
사용자 질문 → 관련 문서 검색 → 적합한 원문과 메타데이터 전달 → 답변 생성
```

검색 단계에서는 질문에 필요한 근거가 확보됐는지 확인한다. 생성 단계에서는 답변이 그 근거를 정확히 사용했는지 살핀다. 예를 들어 적합한 명언이 검색됐더라도 답변에서 문장을 지어내거나 작성자를 잘못 붙였다면 생성 단계의 오류다. 반대로 검색 결과에 재도전을 격려하는 내용이 없다면 답변에 필요한 근거가 부족한 상태다.

## 배운 점

검색 결과를 확인할 때는 가장 높은 점수부터 보는 것보다 질문에서 빠뜨리면 안 되는 조건을 먼저 정하는 편이 판단하기 쉬웠다. 같은 환불 주제라도 완료 여부에 따라 적합성이 달라지는 것처럼, 주제와 상태를 분리해 검증용 질문을 만들면 검색이 어느 조건에서 실패했는지 구체적으로 확인할 수 있다.
