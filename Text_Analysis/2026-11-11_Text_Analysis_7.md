# TIL | 2026-11-11 — LLM API 요청·응답과 분석 결과 관리

LLM API를 사용하면 Python 프로그램에서 정제한 텍스트와 분석 지시를 전달하고, 응답을 받아 원본 데이터와 연결할 수 있다. 오늘은 명언 주제 분류를 예로 들어 요청 준비부터 결과 검증까지의 흐름을 배웠다.

```text
원시 데이터 수집 → 정제 → 프롬프트와 본문 준비 → API 요청
→ 응답 상태와 출력 확인 → 문서 ID로 원본과 연결 → 저장 및 검증
```

## 1. 요청에 담는 정보

대화 화면에서는 사람이 프롬프트를 입력하고 답변을 읽는다. API를 사용하면 프로그램이 요청을 보내고 응답 데이터를 읽으므로 같은 분석 기준을 여러 문서에 적용할 수 있다.

학습자료에서는 OpenAI Responses API의 요청 구조를 예로 들었다.

| 항목 | 역할 |
| --- | --- |
| `model` | 분석에 사용할 모델을 ID로 지정한다. |
| `instructions` | 작업 목적, 분류 기준, 출력 형식을 전달한다. |
| `input` | 실제 분석할 명언 본문을 전달한다. |
| API Key | 서비스가 호출 권한을 확인할 때 사용하는 비밀 인증 정보다. |

아래는 요청 본문의 구조를 보여 주는 학습 예시다. 모델 ID는 자리표시자다.

```json
{
  "model": "<사용 가능한 모델 ID>",
  "instructions": "명언을 성장, 관계, 기타 중 하나로 분류하고 항목 이름만 반환하세요.",
  "input": "Small steps can lead to big changes."
}
```

명언마다 `input`을 바꾸고 동일한 `instructions`를 사용하면 한 가지 분류 기준을 일관되게 적용할 수 있다.

## 2. 응답 읽기와 결과 검증

| 응답 항목 | 확인할 내용 |
| --- | --- |
| `id` | 개별 응답의 식별자. 오류를 조사할 때 문서 ID와 연결해 추적할 수 있다. |
| `status` | 응답 처리 상태. `completed`는 응답 생성이 완료됐음을 나타낸다. |
| `output` | 모델이 생성한 출력 항목. 여러 항목이 들어갈 수 있다. |
| `usage` | `input_tokens`, `output_tokens`, `total_tokens` 등 사용량 정보. |

학습자료의 Python SDK 예시에서는 `response.output_text`로 생성된 텍스트를 읽는다. 이는 SDK의 편의 기능이다. 원본 응답 JSON을 다룰 때는 `output` 안의 항목 유형을 확인해 텍스트를 찾아야 한다.

1. **요청 처리** 단계에서 응답을 받았고 생성이 완료됐는지 확인한다.
2. **출력 존재** 단계에서 필요한 분류 결과가 반환됐는지 확인한다.
3. **형식 검증** 단계에서 출력이 `성장`, `관계`, `기타` 중 하나인지 확인한다.
4. **정확성 검증** 단계에서 분류가 명언의 내용과 판단 기준에 맞는지 확인한다.

예를 들어 *Kindness makes relationships stronger.*에 `성장`이 반환되면 허용값 검사에는 통과하지만, 관계를 주제로 보는 분류 기준에는 맞지 않는다. 반대로 `성장에 관한 명언입니다.`는 뜻을 이해할 수 있어도 항목 이름 하나만 요구한 형식에는 맞지 않는다.

## 3. 여러 문서의 처리 상태 기록

DataFrame에서는 원본 `text`와 생성된 `category`를 별도 컬럼에 두고 문서 ID로 연결한다. 처리 상태와 분류값도 분리하면 실패한 문서만 찾아 다시 처리할 수 있다.

| 문서 ID | 처리 상태 | category |
| --- | --- | --- |
| Q001 | 성공 | 성장 |
| Q002 | 성공 | 관계 |
| Q003 | 요청 실패 | 빈 값 |
| Q004 | 성공 | 기타 |

100건 중 4건의 요청이 실패했다면 성공한 96건과 실패한 4건을 모두 기록한다. `기타`는 분류 기준에 따라 선택한 결과이므로, 요청 실패에는 별도 상태를 남긴다.

| 오류 | 먼저 확인할 사항 |
| --- | --- |
| HTTP 400 | 모델 ID, 입력값, 요청 항목과 형식 |
| HTTP 401 | API Key와 인증 설정 |
| HTTP 429 | 오류 세부 내용, 요청 빈도, 토큰 한도 또는 사용량 제한 |
| HTTP 5xx | 서버 측 오류와 서비스 상태 |
| 연결 오류·시간 초과 | 네트워크 연결과 이전 요청의 처리 상태 |

인증이나 요청 형식 오류는 원인을 수정한 뒤 다시 요청한다. 일시적인 호출 제한이나 서버 오류는 잠시 기다렸다가 재시도할 수 있다. 시간 초과 등 처리 여부가 불분명한 경우에는 이전 요청 상태를 확인해 중복 처리와 비용을 줄인다.

## 4. 사용량과 입력 데이터 관리

모델과 입력·출력 토큰 수, 호출 횟수는 전체 비용에 영향을 준다. 문서마다 같은 지시를 보내면 그 지시도 각 요청의 입력에 포함된다. 분류 결과가 항목 하나면 충분한 작업에서는 출력 형식을 짧게 정해 불필요한 토큰을 줄일 수 있다. 실제 비용은 모델의 요금과 응답에 기록된 사용량을 기준으로 확인한다.

API Key는 환경변수나 별도의 비밀 설정에 저장하고 서버 측에서 사용한다. 고객 리뷰나 상담 기록을 외부 API에 전달하기 전에는 데이터 활용 권한과 서비스의 데이터 처리 정책을 확인한다. 분석에 필요하지 않은 이름, 연락처, 주문번호 등은 제거하거나 비식별 처리한다.

## 배운 점

분류 결과를 집계할 때 요청 실패를 `기타`로 채우면 범주별 건수와 처리 성공률이 함께 왜곡된다. 문서 ID에 원문, 처리 상태, 검증된 분류값을 각각 연결하면 재처리할 행과 분류 기준을 다시 검토할 행을 구분할 수 있다.
