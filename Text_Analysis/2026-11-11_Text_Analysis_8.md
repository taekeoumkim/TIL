# TIL | 2026-11-11 — 구조화된 출력과 여러 문서의 결과 검증

오늘은 `quotes_clean.csv`의 명언을 분류하고 요약하는 사례를 통해 출력 스키마를 설계하고, 여러 분석 결과를 원본 문서에 연결하는 방법을 배웠다.

## 1. JSON과 출력 스키마

명언의 주제와 요약을 각각 DataFrame 컬럼에 저장하려면 응답에서 두 값을 구분할 수 있어야 한다. 구조화된 출력에서는 `category`와 `summary`처럼 필드 이름을 미리 정하고, JSON Schema로 각 필드의 자료형과 허용값을 정의한다.

```json
{
  "type": "object",
  "properties": {
    "category": {
      "type": "string",
      "enum": ["성장", "관계", "기타"]
    },
    "summary": {
      "type": "string"
    }
  },
  "required": ["category", "summary"],
  "additionalProperties": false
}
```

| 스키마 요소 | 적용한 규칙 |
| --- | --- |
| `type` | 전체 결과는 객체, 각 필드의 값은 문자열이다. |
| `properties` | `category`와 `summary`를 정의한다. |
| `enum` | 분류값을 성장·관계·기타로 제한한다. |
| `required` | 두 필드를 모두 포함해야 한다. |
| `additionalProperties: false` | 정의한 두 필드만 허용한다. |

예를 들어 *Small steps can lead to big changes.*의 기대 출력은 아래와 같다.

```json
{
  "category": "성장",
  "summary": "작은 노력이 큰 변화를 만들 수 있다는 의미"
}
```

프롬프트에서 JSON 형식을 요청하면 모델에 원하는 형태를 전달할 수 있다. 지원되는 API의 **Structured Outputs** 기능은 스키마를 사용해 필수 필드, 자료형, 허용값을 제한한다. 응답 거부나 생성 중단이 발생할 수 있으므로 응답 상태와 실제 결과의 존재 여부도 확인한다.

## 2. 여러 문서의 결과를 원본과 연결하기

모든 명언에 같은 분류 기준과 스키마를 적용한다. 이 사례에서는 학습·노력·도전·변화를 `성장`, 우정·배려·소통을 `관계`, 나머지를 `기타`로 분류한다.

| 처리 방식 | 원본과 연결하는 방법 | 확인할 점 |
| --- | --- | --- |
| 문서별 요청 | 프로그램에서 각 요청의 `document_id`를 기록한다. | 요청 수가 늘지만 실패한 문서를 찾기 쉽다. |
| 한 요청에 여러 문서 포함 | 입력과 결과에 문서별 `document_id`를 포함한다. | 입력 크기와 결과 누락·중복·혼동 여부를 확인한다. |

결과가 `Q003 → Q001 → Q002` 순서로 돌아와도 `document_id`로 연결하면 각 결과를 올바른 원본 행에 붙일 수 있다. 문서 ID는 원본 레코드의 식별자이며, API 응답 ID는 개별 응답을 추적하는 데 쓰인다. 분석용 테이블에서는 원문과 작성자 옆에 `category`, `summary`를 별도 컬럼으로 저장해 원문과 비교할 수 있게 한다.

## 3. 출력 오류·누락·요청 실패 구분하기

| 유형 | 예시 | 확인할 사항 |
| --- | --- | --- |
| 출력 형식 오류 | `관계` 대신 허용 목록에 없는 `인간관계` 반환 | 필수 필드와 자료형, 허용값을 검사한다. |
| 결과 누락 | 요청에 포함한 `Q003`의 결과가 없음 | 입력 ID와 출력 ID를 대조한다. |
| 요청 실패 | `Q004`의 API 요청이 완료되지 않음 | 응답 상태와 오류 원인을 확인한다. |
| 매핑 오류 | 같은 문서 ID가 두 번 나오거나 등록되지 않은 ID가 반환됨 | 출력 ID의 유일성과 원본 ID의 존재 여부를 검사한다. |

입력과 출력이 각각 5건이어도 한 결과가 중복되고 다른 결과가 누락될 수 있다. 따라서 건수와 ID를 함께 확인한다. 문서당 결과 하나가 필요한 작업이라면 정상 결과는 각 입력 ID에 정확히 하나씩 대응해야 한다.

처리 결과는 `document_id`, `category`, `status`, `error_reason`으로 기록할 수 있다. 실패한 문서는 분류값을 비워 두고 상태와 원인을 기록한다. `기타`는 분석 기준에 따라 선택된 범주이므로 실패를 이 값으로 기록하면 집계가 왜곡된다. 일시적 오류는 해당 문서의 이전 처리 여부를 확인한 뒤 재시도를 검토하고, 인증이나 요청 형식 오류는 먼저 원인을 수정한다.

## 4. 구조 검증과 내용 평가

*Kindness makes relationships stronger.*에 `category: 성장`과 문자열 요약이 반환되면 스키마 검사는 통과할 수 있다. 그러나 배려와 인간관계에 관한 명언이므로 정의한 기준에는 `관계`가 더 적합하다.

| 검증 단계 | 확인할 내용 |
| --- | --- |
| 처리 검증 | 요청이 완료됐으며 대상 문서별 결과가 있는가? |
| 구조 검증 | 결과가 필수 필드, 자료형, 허용값 규칙을 충족하는가? |
| 내용 평가 | 분류가 기준에 맞고 요약이 원문의 핵심 의미를 보존하는가? |

## 배운 점

여러 문서의 분석 결과를 집계하려면 스키마 설계와 함께 문서별 상태를 기록할 방법도 정해야 한다. 특히 ID가 중복된 결과는 건수 검사만으로 발견하기 어려우므로, 원본과 연결하기 전에 ID별 대응을 검사해야 한다.
