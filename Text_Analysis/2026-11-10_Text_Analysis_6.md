# TIL | 2026-11-10 — 텍스트 분석을 위한 프롬프트 설계

오늘은 LLM에 분석 목적과 판단 기준을 전달하고, 결과를 후속 분석에 쓸 수 있는 형식으로 받는 방법을 배웠다. 같은 텍스트를 사용해도 정보 추출, 분류, 요약에서 요구하는 결과와 검증 기준은 달라진다.

## 1. 프롬프트를 구성하는 네 가지 요소

| 요소 | 명언 주제 분류에 적용한 예 |
| --- | --- |
| 작업 목적 | 명언의 주요 주제를 분류한다. |
| 입력 데이터 | `quotes_clean.csv`의 `text` 컬럼에서 명언 본문을 가져온다. |
| 판단 기준 | 노력·도전·변화는 `성장`, 우정·배려·소통은 `관계`, 나머지는 `기타`로 분류한다. 여러 주제가 있으면 가장 중심이 되는 주제 하나를 선택한다. |
| 출력 형식 | 허용된 항목의 이름 하나만 반환한다. |

“다음 명언을 분석해 주세요”라고 요청하면 요약, 의미 설명, 주제 분류가 모두 가능한 해석이다. 위 기준을 명시하면 *Small steps can lead to big changes.*에 대해 `성장`이라는 출력을 기대할 수 있다.

`성장`, `주제: 성장`, `성장에 관한 명언입니다.`는 의미가 비슷하지만 DataFrame에서 그대로 집계하면 서로 다른 문자열이다. 프롬프트에 허용 범주와 형식을 적고, 반환값이 실제로 그 조건을 충족하는지 확인한다.

## 2. Zero-shot과 Few-shot

| 방식 | 프롬프트 구성 | 적용 상황 |
| --- | --- | --- |
| Zero-shot | 정답 예시 없이 작업 지시, 판단 기준, 출력 조건을 제공한다. | 범주 정의와 선택 규칙만으로 작업을 충분히 설명할 수 있을 때 사용한다. |
| Few-shot | 같은 지시에 소수의 입력·정답 쌍을 추가한다. | 범주 경계가 애매하거나 특정 유형을 반복해서 잘못 분류할 때 검토한다. |

예를 들어 “상품 품질은 괜찮지만 배송이 너무 늦었어요”라는 리뷰의 기대 분류는 `배송`이다. Few-shot에서는 아래처럼 기준이 실제 문장에 어떻게 적용되는지 보여 줄 수 있다.

| 입력 리뷰 예시 | 기대 분류 | 보여 주는 기준 |
| --- | --- | --- |
| 배송이 일주일 넘게 걸렸어요. | 배송 | 배송 속도에 대한 불만 |
| 제품이 고장 난 상태로 도착했어요. | 상품 | 도착을 언급하더라도 불만의 대상은 상품 상태 |
| 품질은 좋지만 가격이 너무 비싸요. | 가격 | 여러 대상 중 부정적으로 평가한 항목을 선택 |

예시는 정답의 정확성, 실제 분석 데이터와의 유사성, 범주 경계를 설명하는 정도를 기준으로 고른다. 상품 파손 사례를 `가격`으로 표시하면 범주 정의와 예시가 충돌한다. Zero-shot과 Few-shot을 비교할 때는 동일한 평가 데이터로 분류 정확도와 출력 형식 준수 여부를 확인한다.

## 3. 같은 리뷰에 세 가지 프롬프트 적용하기

> 배송은 빨랐지만 상품이 파손되어 도착했습니다. 교환을 요청합니다.

| 작업 | 프롬프트에 넣을 조건 | 기대 출력 |
| --- | --- | --- |
| 정보 추출 | 배송 상태, 상품 문제, 고객 요청을 항목별로 반환한다. 원문에서 확인할 수 없는 항목은 `확인 불가`로 표시한다. | 배송 상태는 빠름, 상품 문제는 파손, 고객 요청은 교환 |
| 텍스트 분류 | 배송·상품·가격의 기준을 정의한다. 주요 불만 하나를 고르고 해당 범주가 없으면 `기타`를 반환한다. 항목 이름만 출력한다. | `상품` |
| 텍스트 요약 | 배송 상태, 상품 문제, 고객 요청을 포함해 한 문장으로 정리한다. 각 사실을 원문과 일치시킨다. | 배송은 빨랐으나 상품이 파손되어 도착했으며 고객은 교환을 요청했다. |

정보 추출에서 파손 원인까지 요구한다면 결과는 `확인 불가`다. 분류에서는 배송이 언급됐더라도 긍정적으로 평가됐으므로 상품 파손이 주요 불만이다. 요약에서는 배송 속도와 고객 요청을 함께 보존해야 한다. 이를 배송 지연이나 환불 요청으로 바꾸면 원문의 사실이 달라진다.

## 4. 오류 유형을 기준으로 프롬프트 개선하기

| 관찰한 오류 | 바꿔 볼 조건 |
| --- | --- |
| 요약 대신 의미를 설명함 | 수행할 작업과 필요한 분량을 명시한다. |
| 비슷한 범주를 반복해서 혼동함 | 각 범주의 정의와 선택 규칙을 보완하고 경계 사례를 Few-shot 예시로 검토한다. |
| 허용하지 않은 범주나 설명을 덧붙임 | 허용값, 선택 개수, 반환 형식을 명시한다. |
| 원문에 없는 사실을 추가함 | 원문에서 확인되는 정보만 사용하도록 범위를 정하고 누락값 표기를 지정한다. |
| 요약에서 중요한 사실이 빠짐 | 반드시 포함할 항목을 명시한다. |

수정 전후에는 같은 평가 데이터를 사용한다. 추출은 항목별로 원문에 근거하는지, 분류는 정해진 기준과 허용 범주를 따르는지, 요약은 핵심 사실을 빠뜨리거나 바꾸지 않았는지 각각 비교한다.

## 배운 점

리뷰에 어떤 단어가 등장하는지와 고객이 실제로 무엇에 불만을 느끼는지를 구분하는 규칙이 필요했다. 배송과 상품이 함께 언급되는 리뷰를 평가 데이터에 포함하면, 모델이 언급된 대상을 그대로 분류하는지 실제 불만을 파악하는지 확인할 수 있다.
