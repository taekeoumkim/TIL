# TIL | 2026-11-12 — LLM 텍스트 분석 결과 평가와 개선

오늘은 고객 리뷰와 명언의 분석 결과를 평가하고, 프롬프트나 워크플로우 변경이 실제 개선으로 이어졌는지 확인하는 방법을 배웠다.

## 1. 정확성과 일관성

| 평가 관점 | 비교 대상 | 확인하는 내용 |
| --- | --- | --- |
| 정확성 | LLM 결과와 검증된 정답 또는 원문 | 분류나 생성 내용이 올바른가? |
| 일관성 | 같은 입력과 설정에서 반복 실행한 결과 | 범주나 핵심 내용이 안정적으로 유지되는가? |

상품 파손 리뷰를 세 번 실행해 `상품`, `상품`, `배송`이 나왔다면 결과가 달라진 사례다. 세 번 모두 `배송`이면 일관성은 높지만, 상품 상태에 대한 불만을 `상품`으로 분류한다는 기준에서는 세 번 모두 오답이다.

## 2. 작업에 맞는 평가 기준

| 작업 | 평가 방법 | 오류 예시 |
| --- | --- | --- |
| 텍스트 분류 | 예측 범주를 정답과 비교한다. 정확도와 범주별 오류 사례를 함께 확인한다. | 상품 파손을 배송 불만으로 분류했다. |
| 정보 추출 | 필수 항목이 모두 있는지, 값이 원문과 일치하는지 항목별로 확인한다. 의미가 같은 표현을 어떻게 처리할지도 미리 정한다. | 교환 요청을 환불 요청으로 추출했다. |
| 텍스트 요약 | 핵심 사실이 유지됐는지, 중요한 내용이 빠지거나 근거 없는 내용이 추가됐는지 원문과 대조한다. | 빠른 배송을 배송 지연으로 바꿨다. |

분류 정확도(Accuracy)는 **정답과 일치한 문서 수 ÷ 전체 평가 문서 수**다. 평가 문서 4개 중 3개를 맞혔다면 75%다. 이 수치와 함께 어떤 범주에서 오답이 반복되는지 보면 수정할 기준을 찾기 쉽다. 요약은 표현이 여러 가지일 수 있으므로 원문의 사실과 의미를 기준으로 평가한다.

평가 데이터에는 문서 ID, 원문, 사람이 확인한 정답 또는 평가 기준을 기록한다. 배송과 상품이 함께 언급되는 리뷰처럼 범주 경계를 판단해야 하는 사례도 포함한다.

## 3. 같은 평가 데이터로 방식 비교하기

프롬프트를 비교할 때는 평가 문서, 정답 기준, 모델과 생성 설정을 같게 유지한다. 기준 방식(Baseline)을 먼저 정하고, Few-shot 프롬프트에 넣는 예시는 평가 문서와 분리한다.

| 학습자료의 가상 비교 | 기준 방식 | 비교 방식 | 해석 |
| --- | --- | --- | --- |
| 명언 분류 6건 | Zero-shot 4/6 (66.7%) | Few-shot 5/6 (83.3%) | Q04는 개선됐고 Q06은 두 방식 모두 오답이었다. |
| 명언 분류·요약 10건 | 단일 호출은 분류 8/10, 사실을 유지한 요약 8/10 | 순차 처리는 분류 9/10, 사실을 유지한 요약 8/10 | 분류 정답은 한 건 늘었고 문서당 호출은 1회에서 2회로 증가했다. |

정확도 외에도 반복 실행의 일관성, 출력 형식 준수 여부, 처리 시간과 토큰 사용량을 비교한다. 순차 처리에서는 첫 단계의 오분류가 후속 요약에 영향을 줬는지도 확인한다. 위 수치는 소규모 가상 사례이므로 적용 방식은 실제 평가 데이터에서 필요한 품질과 비용을 기준으로 결정한다.

## 4. 오류 원인에 맞춰 개선하기

> 상품 품질은 괜찮지만 배송이 너무 늦었어요.

이 리뷰가 `상품`으로 분류됐다면, 범주 이름만 제시한 프롬프트에 **실제로 불만을 표현한 대상**을 기준으로 고르라는 규칙과 범주별 정의를 추가할 수 있다. 이 경우 기대 결과는 `배송`이다.

| 발견한 오류 | 검토할 변경 |
| --- | --- |
| 비슷한 범주 혼동 | 범주 정의와 선택 기준을 명확히 하고 경계 사례를 예시로 추가한다. |
| 원문에 없는 정보 생성 | 원문에서 확인된 사실을 사용하도록 지시하고, 근거가 없는 항목의 표기 방법을 정한다. |
| 요약에서 핵심 정보 누락 | 반드시 포함해야 하는 사실을 지정한다. |
| 출력 형식 오류 | 구조화된 출력과 스키마 검증을 적용한다. |
| 결과 누락 | 문서별 처리 상태를 확인하고 필요한 항목을 다시 처리한다. |
| 이전 단계의 오류가 후속 분석에 영향 | 중간 결과와 후속 단계에 전달한 원문을 확인하고 단계 구성을 검토한다. |

변경 후에는 같은 평가 데이터에서 개선된 오류, 남은 오류, 새로 생긴 오류를 문서별로 확인한다. 수정에 사용하지 않은 별도 데이터에서도 개선 효과가 유지되는지 살핀다.

## 배운 점

상품 파손을 계속 배송 불만으로 분류한다면 출력 형식이나 반복 실행만 확인해서는 원인을 찾기 어렵다. 문서별 정답과 예측을 함께 기록하면 범주 정의를 보완해야 하는 사례를 찾을 수 있고, 변경 후 다른 리뷰의 분류까지 영향을 받았는지 추적할 수 있다.
