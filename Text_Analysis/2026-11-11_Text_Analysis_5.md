## 1. LLM의 역할과 텍스트 생성 방식

LLM(Large Language Model)은 대규모 텍스트 등을 학습한 언어 모델이다. 텍스트 분석에서는 원문과 작업 지시를 받아 특정 항목을 추출하거나, 정해진 범주로 분류하거나, 핵심 내용을 요약할 수 있다.

| 방법 | 텍스트 분석에서의 역할 |
| --- | --- |
| TF-IDF | 단어별 가중치를 계산해 문서의 특징적인 키워드를 찾는다. |
| 텍스트 임베딩 | 텍스트의 의미적 특징을 벡터로 표현해 유사한 문서를 찾는다. |
| LLM | 입력 문맥과 지시사항을 바탕으로 추출·분류·요약 결과를 생성한다. |

생성형 LLM은 입력을 **토큰** 단위로 처리한다. 토큰은 단어 전체, 단어의 일부, 문장부호 등이 될 수 있다. 모델은 앞선 문맥에서 다음에 올 토큰의 확률을 계산하고, 생성된 토큰을 이후 문맥에 포함하면서 응답을 이어 간다. 이 과정에는 학습한 언어 패턴과 문맥적 관계가 반영된다.

```text
입력 텍스트 → 토큰 단위 처리 → 다음 토큰 예측 및 생성 → 문맥에 추가 → 반복
```

## 2. 입력 구성과 작업별 출력

분석에 필요한 입력은 **분석 대상**, **작업 지시**, **참고 정보**로 나눌 수 있다. 리뷰 분류라면 원문이 분석 대상이고, 주요 불만 유형을 고르는 것이 작업 지시다. 허용 범주와 각 범주의 정의를 참고 정보로 제공하면 분류 기준이 명확해진다.

> 환불을 요청한 지 일주일이 지났지만 아직 입금되지 않았습니다.

| 요청한 작업 | 기대 출력 예시 |
| --- | --- |
| 정보 추출 | 경과 기간은 일주일, 환불 상태는 미입금 |
| 텍스트 분류 | `환불 지연` |
| 텍스트 요약 | 환불 요청 후 일주일이 지났으나 입금되지 않았다. |

같은 원문도 요청에 따라 필요한 결과가 달라진다. 한 문장에 여러 평가가 담겼을 때는 작업 범위도 중요하다. 상품에는 만족하고 배송 지연에는 불만인 리뷰에서 주요 불만 유형은 `배송`이지만, 전체 요약에는 상품 만족과 배송 불만을 모두 담을 수 있다.

### 출력 변동성

같은 작업을 반복해도 모델과 생성 설정에 따라 표현이 달라질 수 있다. 요약에서는 원문의 핵심 사실을 보존하는 한 표현 차이를 허용할 수 있다. 분류 결과를 집계할 때는 같은 유형이 `환불 지연`, `환불 미완료`, `환불 처리 문제`로 흩어질 수 있으므로 허용 범주와 출력 형식을 미리 정한다.

### 여러 문서 처리와 컨텍스트 윈도우

여러 리뷰를 함께 분석할 때는 입력과 출력에 **문서 ID**를 붙인다. 예를 들어 `R01`, `R02`, `R03`을 전달하고 `R01`, `R03`의 결과만 받으면 `R02`의 누락을 확인할 수 있다. 결과 건수와 함께 입력 ID별 대응 여부를 확인하면 문서 간 결과가 뒤섞이는 문제도 찾을 수 있다.

**컨텍스트 윈도우**는 모델이 한 번의 처리에서 다룰 수 있는 토큰 범위다. 문서뿐 아니라 지시사항과 대화 내용도 처리 범위에 들어간다. 구체적인 한도와 출력 토큰을 계산하는 방식은 모델마다 다르다. 긴 문서나 많은 리뷰를 분석할 때는 입력 크기를 확인하고 필요에 따라 문서나 작업 묶음을 나눌 수 있다.

## 3. LLM의 한계와 결과 검증

**환각(Hallucination)**은 근거가 없거나 사실과 다른 내용을 생성하는 현상이다. 문장이 자연스럽더라도 각 항목이 원문에 근거하는지 확인해야 한다.

> 상품이 고장 난 상태로 도착했습니다. 교환을 요청합니다.

| 항목 | 분석 오류 예시 | 원문을 기준으로 판단 |
| --- | --- | --- |
| 고장 원인 | 배송 중 충격 | 원인 정보가 없어 확인 불가 |
| 고객 요청 | 환불 | 고객은 교환을 요청함 |

정보 추출과 요약에서는 원문에 없는 추측이 추가됐는지, 중요한 사실이 바뀌거나 빠졌는지 살핀다. 확인할 수 없는 항목은 `확인 불가` 등으로 표시한다. 교환 요청을 환불로 기록하면 이후 집계까지 영향을 받는다.

분류에서는 **정확성**과 **일관성**을 따로 확인한다. 상품 고장 리뷰에 허용 범주인 `배송`을 반환했다면 형식은 맞지만 분류는 틀렸다. 올바른 유형을 `상품`과 `제품 문제`로 섞어 저장하면 분류 의도는 비슷해도 범주별 집계가 어려워진다.

| 발견한 문제 | 먼저 확인할 사항 |
| --- | --- |
| 근거 없는 내용이 추가됨 | 입력 원문에서 해당 사실을 확인할 수 있는가? |
| 잘못된 범주가 반환됨 | 범주의 정의와 분류 기준이 명확한가? |
| 같은 유형에 다른 범주명이 사용됨 | 허용 범주와 출력 형식이 정해져 있는가? |
| 필요한 항목이나 문서 결과가 빠짐 | 추출 항목이 지정됐고 모든 입력 ID의 결과가 반환됐는가? |

업무 데이터에 이름이나 연락처가 포함된 경우, 외부 LLM API에 전송하기 전에 데이터 활용 권한과 서비스의 데이터 처리 정책을 확인한다. 필요한 경우 개인정보를 제거하거나 비식별 처리한다.

## 배운 점

리뷰를 분석할 때는 모델에 넣을 문장뿐 아니라 **결과를 어디에 쓸지** 먼저 정해야 한다. 사람이 읽는 요약이라면 핵심 사실을 보존하는지 확인하고, DataFrame에 저장해 집계할 분류 결과라면 허용 범주와 문서 ID까지 검증해야 한다. 특히 원문에 근거가 없는 항목을 빈칸 없이 채우려 하면 추측이 데이터로 저장될 수 있으므로, 확인 가능한 정보와 확인할 수 없는 정보를 구분하는 기준이 필요하다.
