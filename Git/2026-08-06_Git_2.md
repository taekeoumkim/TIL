## Git - Branch

### Branch란?

브랜치는 파일이나 폴더를 복사해 만드는 것이 아니라 **특정 커밋을 가리키는 가벼운 포인터(참조값)**이다. 따라서 브랜치를 생성하는 작업은 빠르고 저장 공간도 거의 사용하지 않는다.

브랜치에서 커밋을 추가하면 해당 브랜치의 포인터만 앞으로 이동하고, 다른 브랜치는 그대로 유지된다.

```text
A ← B ← C ← main
            ↑ HEAD

feature/login 생성 후

A ← B ← C ← main
            ↑ feature/login
            ↑ HEAD

feature/login에서 커밋 추가 후

A ← B ← C ← D ← E ← feature/login
            ↑ main
```

### HEAD란?

`HEAD`는 현재 내가 작업하고 있는 브랜치 또는 커밋을 가리키는 특수 포인터이다.

브랜치를 전환하면 다음과 같이 동작한다.

1. `HEAD`가 새로운 브랜치로 이동한다.
2. 해당 브랜치가 가리키는 커밋의 스냅샷이 인덱스에 반영된다.
3. 인덱스의 내용이 워킹 디렉터리에 반영된다.

따라서 브랜치를 전환하면 작업 중인 파일도 해당 브랜치의 최신 커밋 상태로 변경된다.

### Branch 명령어

```bash
# 브랜치 목록 조회
git branch

# 원격 브랜치를 포함한 전체 브랜치 조회
git branch -a

# 브랜치 생성
git branch feature/login

# 브랜치 삭제
git branch -d feature/login

# 강제 삭제
git branch -D feature/login
```

브랜치를 생성한다고 바로 해당 브랜치로 이동하는 것은 아니다.

```bash
# 브랜치 생성 + 전환
git switch -c feature/login

# 브랜치 전환
git switch feature/login
```

`git checkout`도 브랜치 전환에 사용할 수 있지만, 브랜치 전환과 파일 복구 등의 여러 기능을 함께 담당한다. Git 2.23 이후에는 역할이 명확한 `git switch` 사용을 권장한다.

```bash
git checkout feature/login
git checkout -b feature/login
```

### Feature Branch 전략

팀 프로젝트에서는 기능별로 브랜치를 분리해서 개발하는 Feature Branch 전략을 사용할 수 있다.

- `main`은 안정적인 코드 유지
- 여러 기능을 동시에 독립적으로 개발
- 코드 리뷰 후 병합 가능
- 개발 중인 기능이 다른 팀원에게 영향을 주는 것을 방지

브랜치 네이밍 예시는 다음과 같다.

```text
feature/login
feature/user-profile
fix/login-bug
hotfix/긴급수정명
release/버전
```

### 작업 중 브랜치를 전환할 때 주의할 점

커밋하지 않은 변경사항이 대상 브랜치의 파일과 충돌한다면 Git은 브랜치 전환을 중단한다.

따라서 브랜치를 전환하기 전에 변경사항을 커밋하거나 `git stash`로 임시 저장하는 것이 안전하다.

## Git - Merge

브랜치에서 작업한 내용을 `main`에 합치는 과정이 **merge(병합)**이다.

Git은 브랜치의 히스토리 상황에 따라 `Fast-forward merge` 또는 `3-way merge` 방식으로 병합한다.

### Fast-forward Merge

`main`이 `feature` 브랜치의 조상 커밋을 가리키고 있고, `main`에서 별도의 새로운 커밋이 없다면 Fast-forward merge가 발생한다.

이 경우 새로운 병합 커밋을 만들지 않고 `main` 포인터만 `feature`의 최신 커밋으로 이동한다.

```text
A ← B ← C ← D ← E ← feature
            ↑ main

merge 후

A ← B ← C ← D ← E ← feature
                    ↑ main
```

히스토리가 직선으로 이어지고 별도의 병합 커밋이 생성되지 않는다.

### 3-way Merge

두 브랜치가 공통 조상(Base)에서 분기한 뒤 각각 새로운 커밋을 가지고 있다면 3-way merge가 발생한다.

Git은 다음 세 커밋을 비교한다.

- 공통 조상(Base)
- 브랜치 A의 최신 커밋
- 브랜치 B의 최신 커밋

그 결과 새로운 병합 커밋을 생성한다.

```text
A ← B ← C ← main
         ↖ D ← E ← feature

merge 후

A ← B ← C ← M ← main
         ↖   ↗
           D ← E ← feature
```

병합 커밋 `M`은 두 브랜치의 최신 커밋을 부모로 가진다.

### merge 주요 옵션

#### `--no-ff`

Fast-forward가 가능한 상황에서도 병합 커밋을 강제로 생성한다.

```bash
git merge --no-ff feature/login
```

기능이 어디에서 시작해서 어디에서 끝났는지 히스토리에 명확하게 남기고 싶을 때 사용할 수 있다.

#### `--squash`

feature 브랜치의 여러 커밋을 하나로 압축해 스테이징 영역에 올린다. 이후 직접 commit해야 한다.

```bash
git merge --squash feature/login
git commit -m "feat: 로그인 기능 추가"
```

### 히스토리 확인

```bash
git log --graph --oneline --all
```

Fast-forward는 히스토리가 직선으로 이어지는 반면, 3-way merge 또는 `--no-ff`는 병합 커밋이 남아 어떤 작업이 병합되었는지 확인하기 쉽다.

## Git - Rebase

`rebase`는 현재 브랜치의 커밋들을 다른 브랜치의 최신 커밋 위에 다시 적용하여 **선형적인 히스토리**를 만드는 작업이다.

```bash
git rebase main
```

### Rebase 동작 원리

`feature` 브랜치에서 `git rebase main`을 실행하면 다음 순서로 진행된다.

1. `feature`와 `main`의 공통 조상을 찾는다.
2. 공통 조상 이후 `feature`에만 존재하는 커밋을 임시로 저장한다.
3. `feature` 브랜치 포인터를 `main`의 최신 커밋으로 이동한다.
4. 임시 저장한 커밋을 새로운 Base 위에 순서대로 다시 적용한다.

이때 기존 커밋과 내용은 같더라도 **새로운 커밋으로 재생성되기 때문에 커밋 해시가 변경된다.**

```text
rebase 전

A ← B ← C ← main
         ↖ D ← E ← feature

rebase 후

A ← B ← C ← main ← D' ← E' ← feature
```

`D'`, `E'`는 `D`, `E`와 내용은 같지만 새로운 커밋 해시를 가진 커밋이다.

### Merge vs Rebase

| 항목 | Merge | Rebase |
| --- | --- | --- |
| 히스토리 | 분기/병합 구조 | 직선 구조 |
| 병합 커밋 | 생성될 수 있음 | 생성하지 않음 |
| 커밋 해시 | 변경 없음 | 재생성되어 변경됨 |
| 분기 흔적 | 명확하게 남음 | 직선처럼 보임 |
| 공유 브랜치 | 안전 | 위험 |

두 방식은 최종 코드 상태는 같을 수 있지만 히스토리의 모양은 다르다.

### Rebase 실무 선택 기준

가장 중요한 기준은 **다른 사람과 공유된 브랜치인지 여부**이다.

- 개인 `feature` 브랜치: rebase를 사용해 `main`의 변경사항을 반영하고 히스토리를 선형으로 정리할 수 있다.
- 공유 브랜치(`main`, `develop`): rebase하지 않고 merge를 사용한다.

### Rebase의 황금률

> **공유된 커밋은 rebase하지 않는다.**

rebase는 커밋 해시를 변경하기 때문에 이미 원격 저장소에 push된 커밋이나 팀 공용 브랜치의 커밋을 rebase하면 다른 팀원의 히스토리와 불일치가 발생할 수 있다.

개인 브랜치에서 이미 push한 커밋을 rebase해야 하는 경우에는 상황에 따라 다음 명령을 사용할 수 있다.

```bash
git push --force-with-lease
```

## Git - Conflict

Conflict(충돌)는 Git이 두 브랜치의 변경사항을 자동으로 결정할 수 없는 상황이다.

대표적으로 **같은 파일의 같은 줄을 서로 다르게 수정한 경우** 충돌이 발생한다.

충돌은 Git의 오류라기보다, Git이 어느 변경사항을 선택할지 개발자에게 판단을 요청하는 정상적인 과정이다.

### 흔한 충돌 상황

- 두 명이 같은 파일의 같은 라인을 수정
- 한 명이 파일을 삭제하고 다른 사람이 같은 파일을 수정
- 같은 함수나 클래스를 서로 다른 방향으로 리팩토링

### Conflict Marker

충돌이 발생하면 Git은 파일에 충돌 마커를 삽입한다.

```text
<<<<<<< HEAD
현재 브랜치의 내용
=======
병합하려는 브랜치의 내용
>>>>>>> feature/login
```

각 영역의 의미는 다음과 같다.

- `<<<<<<< HEAD` ~ `=======`: 현재 체크아웃된 브랜치의 내용
- `=======` ~ `>>>>>>> feature/login`: 병합하려는 브랜치의 내용

개발자가 최종적으로 남길 내용을 직접 결정한 후 **충돌 마커를 모두 제거해야 한다.**

### Merge Conflict 해결 절차

```bash
# 1. 충돌 파일 확인
git status

# 2. 충돌 파일을 열고 직접 수정
# <<<<<<<, =======, >>>>>>> 제거

# 3. 수정한 파일 스테이징
git add README.md

# 4. 병합 완료
git commit
```

핵심은 **파일 편집 → `git add` → `git commit`** 순서이다.

충돌 마커가 파일에 그대로 남아 있으면 해당 텍스트가 코드에 포함될 수 있으므로 반드시 모두 제거해야 한다.

### Merge를 취소하고 싶다면

충돌이 너무 복잡해 처음부터 다시 시작하고 싶을 때는 merge를 취소할 수 있다.

```bash
git merge --abort
```

## Rebase 중 Conflict

rebase에서는 커밋을 하나씩 순차적으로 다시 적용하기 때문에 충돌이 커밋별로 발생할 수 있다.

충돌을 해결한 후에는 다음 명령으로 상황에 맞게 처리한다.

```bash
# 충돌 해결 후 계속 진행
git add <충돌_파일>
git rebase --continue

# 현재 커밋을 건너뛰기
git rebase --skip

# rebase 전체 취소
git rebase --abort
```

| 옵션 | 동작 | 사용 시기 |
| --- | --- | --- |
| `--continue` | 다음 커밋 재적용 | 충돌 해결 후 |
| `--skip` | 현재 커밋 건너뜀 | 해당 커밋이 불필요할 때 |
| `--abort` | rebase 전체 취소 | 원래 상태로 돌아갈 때 |

## Conflict를 줄이는 방법

충돌 자체를 완전히 없앨 수는 없지만 다음과 같은 방법으로 빈도와 복잡도를 줄일 수 있다.

- 작은 단위로 자주 커밋하고 자주 병합하기
- 기능별로 파일을 분리하기
- feature 브랜치에서 `main`의 변경사항을 주기적으로 반영하기
- 코드 리뷰와 PR 활용하기
- 팀원별 코드 소유권을 명확하게 정하기

## 오늘 배운 내용 정리

오늘은 Git에서 브랜치를 활용해 독립적으로 작업하고, 작업 결과를 merge 또는 rebase를 통해 통합하는 방법을 학습했다.

특히 단순히 명령어를 외우는 것보다 **Git의 커밋 히스토리가 어떻게 변하는지 이해하는 것이 중요하다**고 느꼈다.

### 핵심 정리

1. 브랜치는 커밋을 가리키는 포인터이며 파일 복사가 아니다.
2. `HEAD`는 현재 작업 위치를 가리키는 특수 포인터이다.
3. `git switch`를 이용하면 브랜치를 명확하게 전환할 수 있다.
4. Feature Branch 전략을 사용하면 기능별로 독립적인 개발이 가능하다.
5. Fast-forward merge는 별도의 병합 커밋 없이 브랜치 포인터만 이동한다.
6. 3-way merge는 분기된 두 브랜치를 비교해 병합 커밋을 생성한다.
7. `rebase`는 커밋을 새로운 Base 위에 다시 적용하여 선형적인 히스토리를 만든다.
8. rebase 과정에서는 기존 커밋이 새로운 커밋으로 재생성되어 해시가 변경된다.
9. **공유된 커밋은 rebase하지 않는다.**
10. Conflict는 같은 파일의 같은 부분을 서로 다르게 수정했을 때 발생할 수 있으며, 최종 내용을 직접 결정해 해결한다.
11. Conflict 해결 후에는 충돌 마커를 모두 제거하고 `git add` 후 작업을 완료해야 한다.
12. rebase 중 충돌은 `--continue`, `--skip`, `--abort`로 상황에 맞게 처리한다.

### 실습에서 기억할 명령어

```bash
# Branch
git branch
git branch feature/login
git switch feature/login
git switch -c feature/login

# Merge
git merge feature/login
git merge --no-ff feature/login
git merge --squash feature/login

# History 확인
git log --graph --oneline --all

# Rebase
git rebase main
git rebase --continue
git rebase --skip
git rebase --abort

# Conflict
git status
git add <충돌_파일>
git commit
git merge --abort
```
