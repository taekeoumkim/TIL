# 1. Git이 필요한 이유

AI 프로젝트에서는 작은 코드 변경도 모델 성능이나 서비스 결과에 영향을 줄 수 있다.

Git은 이러한 변경사항을 기록하고 관리하여

- 언제든 이전 버전으로 복구 가능
- 여러 명이 동시에 협업 가능
- 누가 무엇을 변경했는지 추적 가능

하게 만들어준다.

예전처럼

```
final.py
final_v2.py
final_final.py
final_진짜최종.py
```

처럼 파일 이름으로 관리하는 방식보다 훨씬 체계적이다.

---

# 2. Git과 GitHub의 차이

많이 헷갈렸던 부분이다.

|Git|GitHub|
|---|---|
|버전 관리 프로그램|Git 저장소를 호스팅하는 서비스|
|내 컴퓨터에서 동작|온라인 서버|
|GitHub 없이 사용 가능|Git 없이는 사용 불가|

즉,

> Git은 프로그램이고 GitHub는 Git 저장소를 올려두는 서비스이다.

---

# 3. Git의 3영역 모델

Git에서 가장 중요한 개념이다.

```
Working Directory
        │
   git add
        ▼
Staging Area(Index)
        │
 git commit
        ▼
Repository
```

### Working Directory

실제로 코드를 수정하는 공간

### Staging Area

다음 Commit에 포함할 파일을 임시로 모아두는 공간

### Repository

Commit이 영구적으로 저장되는 공간

Git은

```
Working Directory
→ Staging
→ Repository
```

순서로 데이터가 이동한다.

# 4. Git 기본 명령어

상태 확인

```bash
git status
```

변경사항 스테이징

```bash
git add .
```

커밋 생성

```bash
git commit -m "메시지"
```

커밋 전 변경사항 확인

```bash
git diff
```

스테이징된 내용 확인

```bash
git diff --staged
```

# 5. Git 초기 설정

Git을 설치했다고 바로 사용할 수 있는 것은 아니다.

사용자 정보를 먼저 등록해야 한다.

```bash
git config --global user.name "이름"

git config --global user.email "이메일"
```

설정 확인

```bash
git config --list
```

### global과 local

global

- 모든 저장소에 적용

local

- 현재 저장소에만 적용

회사 프로젝트와 개인 프로젝트를 구분할 때 local 설정을 사용할 수 있다.

# 6. GitHub 인증 (SSH)

GitHub와 통신하기 위해 SSH 인증을 설정하였다.

SSH는

- 공개키(Public Key)
- 개인키(Private Key)

두 개의 키를 이용하여 인증한다.

### SSH 생성

```bash
ssh-keygen -t ed25519 -C "email"
```

공개키를 GitHub에 등록한 뒤

```bash
ssh -T git@github.com
```

명령으로 인증을 확인한다.

SSH는 한 번 설정하면 비밀번호를 계속 입력하지 않아도 되기 때문에 개인 개발 환경에서 가장 많이 사용된다.

# 7. 저장소 생성

새 프로젝트

```bash
git init
```

기존 저장소 복사

```bash
git clone 저장소주소
```

### 차이

git init

- 새로운 Git 저장소 생성

git clone

- 기존 저장소와 Commit 이력까지 모두 복사

# 8. .gitignore

Git이 관리하지 않을 파일을 지정하는 파일이다.

대표적으로

```
.env

__pycache__/

*.log

.ipynb_checkpoints/

*.pkl
```

등을 제외한다.

API Key나 로그 파일을 GitHub에 올리지 않도록 해주는 중요한 파일이다.

이미 추적 중인 파일은

```bash
git rm --cached 파일명
```

으로 추적을 해제해야 한다.

# 9. Git Commit 흐름

가장 기본적인 작업 순서는

```text
git status

↓

git add

↓

git commit
```

이다.

Commit 전에는

```bash
git diff
```

Commit 직전에는

```bash
git diff --staged
```

로 변경사항을 확인하는 습관이 중요하다.

# 10. Conventional Commits

커밋 메시지를 일정한 규칙으로 작성하는 방법이다.

|Type|의미|
|---|---|
|feat|새 기능|
|fix|버그 수정|
|docs|문서 수정|
|refactor|리팩토링|
|test|테스트|
|chore|설정 변경|

예시

```text
feat: add login feature

fix: resolve login bug

docs: update README

chore: update .gitignore
```

또한

> **한 Commit에는 하나의 목적만 담는다.**

라는 원칙이 가장 중요하다고 느꼈다.

# 💡 오늘 알게 된 점

- Git은 단순히 코드를 저장하는 프로그램이 아니라 변경 이력을 관리하는 시스템이다.
- Working Directory → Staging Area → Repository의 흐름을 이해하는 것이 Git의 핵심이다.
- Git과 GitHub는 서로 다른 역할을 한다.
- `.gitignore`는 보안과 프로젝트 관리를 위해 반드시 작성해야 한다.
- Commit 메시지는 협업을 위한 기록이므로 의미 있게 작성해야 한다.

---

# 🤔 느낀 점

처음에는 Git 명령어를 외우는 것에 집중했지만, 오늘 학습을 통해 Git은 **파일을 어떤 공간에서 어떻게 관리하는지 이해하는 것이 더 중요하다**는 것을 알게 되었다.

특히 3영역 모델을 이해하니 `git add`와 `git commit`의 역할이 명확하게 구분되었고, 앞으로는 단순히 명령어를 사용하는 것이 아니라 Git이 내부적으로 어떤 과정을 거치는지 생각하면서 사용할 수 있을 것 같다.

또한 `.gitignore`와 SSH 인증처럼 실제 프로젝트에서 반드시 필요한 설정도 함께 배워 실무에서 Git을 사용하는 흐름을 이해하는 데 도움이 되었다.
