# TIL | 2026-11-24 — VLM API와 이미지 정보 구조화

상품 이미지를 API로 전달해 종류·색상·외형·촬영 상황을 추출하고, 결과를 일정한 구조로 관리하는 방법을 배웠다. 요청 처리, 출력 스키마, 실제 이미지와의 사실 일치를 각각 확인하는 과정도 살펴봤다.

## 1. 이미지 입력과 요청·응답 흐름

```text
이미지 준비 → 프롬프트 작성 → 이미지와 텍스트 전송
→ 응답 상태 확인 → 결과 파싱 → 이미지와 대조 → 저장
```

| 입력 방법 | 준비할 정보 |
| --- | --- |
| 이미지 URL | 서비스가 접근할 수 있는 이미지 주소 |
| Base64 데이터 | 로컬 이미지의 바이트를 인코딩한 데이터와 이미지 형식 |
| 파일 ID | 서비스에 업로드한 파일의 식별자 |

학습자료는 OpenAI Responses API에서 이미지와 텍스트를 함께 보내는 구조를 예로 들었다. 텍스트에는 분석 목적과 출력 조건을, 이미지에는 분석할 시각적 데이터를 담는다.

Base64는 바이너리를 텍스트로 표현하는 인코딩이다. 디코딩하면 원본 데이터를 복원할 수 있으므로 민감 정보 보호는 별도로 관리한다. 이미지 특징을 벡터로 추출하는 임베딩과도 역할이 다르다.

```python
import base64
from pathlib import Path

image_data = base64.b64encode(
    Path("sample.jpg").read_bytes()
).decode("utf-8")

image_url = f"data:image/jpeg;base64,{image_data}"
```

JPEG 기준 예시다. PNG 등을 사용할 때는 파일과 데이터 URL의 MIME 형식을 맞춘다. API 키는 환경변수로 관리하고, 학습자료의 `.env` 방식이라면 공개 저장소 업로드 방지 설정도 적용한다.

## 2. 프롬프트와 추출 항목 정의

이미지마다 같은 속성을 비교하려면 추출 항목과 불확실한 값의 처리 규칙을 먼저 정한다.

> 상품 이미지에서 종류, 주요 색상, 외형적 특징, 촬영 상황을 추출하세요. 이미지에서 확인할 수 없는 단일 값은 null로, 확인되는 외형적 특징이 없으면 빈 리스트로 표현하세요. 이미지에서 관찰되는 정보를 근거로 작성하세요.

| 필드 | 자료형 | 용도 |
| --- | --- | --- |
| `product_type` | 문자열 또는 null | 상품 종류 |
| `main_color` | 문자열 또는 null | 주요 색상 |
| `visible_features` | 문자열 리스트 | 보이는 장식·형태 등 |
| `scene` | 문자열 또는 null | 배경과 촬영 상황 |

색상·형태는 이미지에서 관찰하고, 실제 소재·브랜드 등 확정에 추가 정보가 필요한 항목은 확인 가능 여부를 판단한다. 색상 집계에서 `남색`, `네이비`, `짙은 파란색`이 나뉘지 않도록 필요한 경우 범주 정의나 후처리 기준을 둔다.

## 3. Pydantic으로 출력 구조 표현

```python
from pydantic import BaseModel

class ProductInfo(BaseModel):
    product_type: str | None
    main_color: str | None
    visible_features: list[str]
    scene: str | None
```

`str | None`은 문자열 값과 확인 불가 값을 허용하고, `list[str]`은 여러 특징을 담는다. JSON의 `null`은 Python에서 `None`에 대응한다.

학습자료에서는 `client.responses.parse()`에 `text_format=ProductInfo`를 지정하고 `response.output_parsed`로 파싱 결과를 읽는 흐름을 소개했다. 사용하는 모델과 SDK에서 지원하는 입력·출력 조건을 확인해 적용한다. 파싱 결과가 없으면 응답 상태와 거절·미완료 여부를 조사한다.

정상 결과는 `model_dump()`로 딕셔너리로 바꿔 파일이나 DataFrame에 연결할 수 있다. 이미지별 상품 종류·색상·촬영 상황을 집계하기 전에는 추출 오류와 누락을 확인한다.

## 4. 구조와 내용 검증

| 검증 단계 | 확인 사항 |
| --- | --- |
| 요청 처리 | 인증, 입력 형식, 네트워크, 사용 한도에 문제가 있는가? |
| 응답 처리 | 완료된 응답과 필요한 파싱 결과를 얻었는가? |
| 스키마 | 필드와 자료형이 정의에 맞는가? |
| 내용 | 상품·색상·특징이 실제 이미지와 일치하는가? |
| 집계 준비 | 같은 의미의 값이 일관되게 기록됐는가? |

다음은 사람이 이미지에서 정답을 확인했다고 가정한 검증 예시다.

```python
model_output = {
    "product_type": "가방",
    "main_color": "검은색",
    "visible_features": ["손잡이", "금속 장식"],
    "scene": "실내",
}
ground_truth = {
    "product_type": "가방",
    "main_color": "갈색",
    "visible_features": ["손잡이"],
    "scene": "실내",
}

result = ProductInfo.model_validate(model_output)

for field, actual in ground_truth.items():
    predicted = getattr(result, field)
    print(field, predicted == actual)
```

위 결과는 구조 검사를 통과하지만 색상과 외형적 특징에서 불일치한다. 이 비교는 완전 일치 기준이다. 실제 평가에서는 색상 표현의 동의어와 특징 리스트의 순서 등 필드별 의미를 반영한 기준을 먼저 정한다.

## 5. 오류와 실패 상태 관리

| 상황 | 처리 방향 |
| --- | --- |
| 인증·입력 형식 오류 | 키, 환경변수, 이미지와 요청 형식 확인 |
| 사용량 제한·일시적 서버·연결 오류 | 원인과 이전 요청 상태를 확인하고 적절히 재시도 |
| 거절·미완료·파싱 결과 없음 | 실패 또는 검토 필요 상태 기록 |
| 특정 속성 확인 불가 | null로 표현하고 다른 정상 필드와 함께 관리 |
| 잘못된 추출·근거 없는 특징 생성 | 원본 이미지와 비교하여 재검토 |

SDK의 자동 재시도 동작도 고려하여 불필요한 중복 요청을 줄인다. 확인할 수 없는 속성과 전체 분석 실패는 처리 상태로 구분해 기록한다. 요청 규모와 이미지·텍스트 사용량에 따른 비용, 외부 전송 권한과 개인정보도 확인한다.

검증용 이미지는 상품 종류와 촬영 조건을 다양하게 포함하도록 고른다. 사람이 정답을 기록한 뒤 필드별 오류와 이미지 유형을 조사하고, 프롬프트 변경 전후를 같은 검증 데이터에서 비교한다.

## 배운 점

VLM의 자연어 설명을 표로 집계하려면 먼저 필드와 값의 표현 기준을 정해야 한다. 정상 JSON에도 실제로 없는 장식이 들어갈 수 있으므로, 스키마 검증과 함께 이미지에 근거한 속성인지 확인하는 평가가 필요하다는 점을 배웠다.
