# 2026-08-04 TIL

## 문제 정의 기초

### 문제 정의란?

문제 정의는 **해결하려는 상황을 명확하게 설명하고, 데이터로 확인할 수 있는 질문으로 바꾸는 과정**이다.

데이터 분석은 단순히 데이터를 많이 보는 것이 아니라 의사결정에 필요한 근거를 찾는 과정이다. 따라서 분석을 시작하기 전에 무엇을 해결하려는지 명확하게 정의해야 한다.

문제 정의를 할 때는 다음 질문을 확인해야 한다.

- 우리는 지금 무엇이 궁금한가?
- 어떤 상황을 개선하고 싶은가?
- 이 문제가 왜 중요한가?
- 어떤 데이터를 보면 문제를 확인할 수 있는가?
- 분석 결과를 바탕으로 어떤 의사결정을 해야 하는가?

문제가 모호하면 어떤 데이터를 수집해야 하는지, 어떤 지표를 봐야 하는지, 어떤 분석 방법을 사용해야 하는지 결정하기 어렵다.

### 막연한 문제와 좋은 문제 정의

다음과 같은 표현은 범위가 넓고 분석 방향이 명확하지 않다.

```text
매출이 안 좋아요.
고객 반응이 별로예요.
서비스가 잘 안 되는 것 같아요.
마케팅 효과를 알고 싶어요.
사용자 데이터를 분석해 주세요.
```

이를 분석 가능한 질문으로 구체화할 수 있다.

```text
최근 3개월 동안 월별 매출이 전년 동기 대비 얼마나 감소했는가?
신규 고객과 기존 고객 중 어느 집단에서 매출 감소가 더 크게 나타나는가?
광고 유입 고객의 구매 전환율이 지난 캠페인 대비 얼마나 낮아졌는가?
회원가입 이후 첫 구매까지 어느 단계에서 이탈이 가장 많이 발생하는가?
```

좋은 문제 정의는 다음과 같은 특징을 가진다.

1. **구체적이어야 한다.**
2. **데이터로 답할 수 있어야 한다.**
3. **의사결정과 연결되어야 한다.**
4. **분석 범위가 적절해야 한다.**

즉, 좋은 분석 질문은 단순히 궁금한 것을 묻는 것이 아니라 **분석 결과를 통해 실제 행동을 결정할 수 있는 질문**이어야 한다.

### 문제 정의의 기본 구조

문제를 정의할 때는 다음과 같은 구조로 정리할 수 있다.

```text
현재 상황
   ↓
문제
   ↓
영향
   ↓
분석 질문
   ↓
의사결정
```

예를 들어 이커머스의 전환율 하락을 분석한다고 하면:

- **현재 상황**: 최근 3개월 동안 방문자는 유지되고 있지만 구매 건수가 감소하고 있다.
- **문제**: 구매 전환율이 하락하고 있다.
- **영향**: 전환율 하락은 매출 감소와 광고비 효율 저하로 이어질 수 있다.
- **분석 질문**: 어느 유입 채널, 고객군, 구매 단계에서 전환율 하락이 가장 크게 발생했는가?
- **의사결정**: 광고 예산, 상품 상세 페이지, 장바구니, 결제 단계 중 어디를 우선 개선할 것인가?

### 문제 정의가 중요한 이유

문제 정의가 잘못되면 분석을 열심히 하더라도 실제 문제를 해결하지 못할 수 있다.

예를 들어 실제 문제가 결제 단계의 오류인데 이를 "광고 효율이 낮다"라고 정의하면 광고 클릭률, 유입량 등의 데이터만 계속 분석하게 된다.

결국 실제 원인인 결제 오류는 해결하지 못한다.

> **많은 데이터를 보는 것보다 올바른 문제를 향해 데이터를 보는 것이 중요하다.**

## 주요 서비스 지표 이해

### 서비스 지표란?

서비스 지표는 **사용자가 서비스 안에서 어떻게 행동하는지를 확인하기 위한 숫자**이다.

웹사이트, 앱, 쇼핑몰, SaaS 등의 서비스는 사용자의 행동 데이터를 기록하고 이를 통해 서비스가 잘 작동하고 있는지, 어느 부분에서 문제가 발생하는지 확인할 수 있다.

서비스 지표를 통해 다음과 같은 질문에 답할 수 있다.

- 얼마나 많은 사용자가 방문하는가?
- 방문자 중 몇 명이 가입하는가?
- 가입한 사용자 중 몇 명이 구매하는가?
- 구매한 사용자가 다시 돌아오는가?
- 어느 단계에서 가장 많은 사용자가 이탈하는가?

### 사용자 행동 흐름과 AARRR

서비스 지표는 일반적으로 사용자의 행동 흐름을 따라간다.

```text
Acquisition → Activation → Retention → Referral → Revenue
    유입          활성화        유지         추천        수익
```

각 단계에 따라 확인해야 할 지표가 달라진다.

| 단계 | 주요 지표 |
| --- | --- |
| 방문 | 방문자 수, 유입 채널, 페이지뷰 |
| 가입/활성화 | 가입 전환율, 활성 사용자 수 |
| 사용 | 세션 수, 사용 시간 |
| 구매 | 구매 전환율, 객단가, 매출 |
| 유지 | 재방문율, 리텐션, 이탈률 |

### 방문자 수와 활성 사용자 수

**방문자 수**는 특정 기간 동안 서비스에 방문한 사용자 수이다.

방문자가 증가하면 관심이 늘고 있다고 볼 수 있지만, 방문자 수만으로 서비스의 성공 여부를 판단할 수는 없다.

방문자가 많더라도 가입이나 구매로 이어지지 않을 수 있기 때문이다.

**활성 사용자 수**는 특정 기간 동안 실제로 서비스를 사용한 사용자 수이다.

대표적으로 다음 지표가 있다.

- DAU: Daily Active Users
- WAU: Weekly Active Users
- MAU: Monthly Active Users

단순 가입자 수보다 실제 서비스 사용 정도를 파악하는 데 유용하다.

### 전환율과 이탈률

**전환율**은 특정 행동을 완료한 사용자의 비율이다.

```text
전환율 = 전환 완료 사용자 수 / 전체 대상 사용자 수 × 100
```

예를 들어 상품 상세 페이지를 방문한 1,000명 중 50명이 구매했다면 구매 전환율은 5%이다.

전환율은 사용자가 어느 단계에서 행동을 멈추는지 확인하는 데 중요한 지표이다.

**이탈률**은 특정 단계에서 사용자가 더 이상 다음 행동으로 넘어가지 않는 비율이다.

예를 들어 장바구니에 상품을 담았지만 결제하지 않고 나간 사용자의 비율을 장바구니 이탈률로 볼 수 있다.

이탈률이 높다면 다음과 같은 원인을 확인할 수 있다.

- 특정 기기나 브라우저의 문제
- 특정 유입 채널의 문제
- 결제 과정의 오류
- 사용하기 어려운 UI
- 예상하지 못한 비용이나 정책

### 리텐션

리텐션은 **사용자가 일정 기간 후에도 서비스를 계속 사용하는 비율**이다.

예를 들어 앱을 설치한 사용자 중 7일 후에도 다시 접속한 사용자의 비율을 7일 리텐션이라고 한다.

신규 사용자를 많이 확보하는 것도 중요하지만 사용자가 계속 돌아오지 않는다면 서비스가 안정적으로 성장하기 어렵다.

리텐션이 낮다면 다음과 같은 질문을 해볼 수 있다.

- 첫 사용 경험이 어렵지는 않았는가?
- 사용자가 반복적으로 돌아올 이유가 충분한가?
- 콘텐츠나 기능의 가치가 명확한가?
- 알림이나 리마인드가 적절한가?
- 사용자가 초기에 이탈하는 지점은 어디인가?

### 객단가

객단가는 **고객이 한 번 구매할 때 평균적으로 지출하는 금액**이다.

```text
객단가 = 총 매출 / 주문 수
```

매출은 단순히 고객 수만으로 결정되지 않는다.

```text
매출
= 구매하는 고객 수 × 구매 빈도 × 객단가
```

따라서 방문자 수가 그대로여도 객단가가 증가하면 매출이 증가할 수 있고, 방문자가 늘더라도 객단가가 크게 떨어지면 매출이 기대만큼 증가하지 않을 수 있다.

### 서비스 지표는 함께 봐야 한다

하나의 지표만 보면 잘못된 결론을 내릴 수 있다.

예를 들어 방문자 수가 증가했더라도 전환율이 낮아졌다면 단순히 좋은 상황이라고 판단하기 어렵다.

또한 매출이 증가했다고 해서 반드시 건강한 성장이라고 볼 수도 없다. 광고비를 과도하게 사용했거나 일부 고액 고객에 의존한 결과일 수도 있다.

따라서 다음과 같이 사용자 행동의 흐름을 연결해서 봐야 한다.

```text
방문
 ↓
가입
 ↓
활성화
 ↓
구매
 ↓
재방문
```

> **지표 하나의 변화보다 여러 지표 사이의 관계를 보는 것이 중요하다.**

## 데이터 기반 의사결정 프로세스

### 데이터 기반 의사결정이란?

데이터 기반 의사결정은 감이나 직관만으로 판단하지 않고 **데이터를 근거로 더 나은 결정을 내리는 방식**이다.

단순히 데이터를 보고 결정하는 것이 아니라 다음 전체 과정을 의미한다.

```text
문제 정의
   ↓
지표 설정
   ↓
데이터 수집 및 분석
   ↓
해석 및 의사결정
   ↓
액션 실행
   ↓
결과 검증
   ↺
```

중요한 점은 이 과정이 한 번으로 끝나지 않는다는 것이다.

액션을 실행한 뒤 결과를 다시 확인하고, 필요하다면 문제 정의와 지표를 수정하면서 반복한다.

### 1. 문제 정의

첫 번째 단계는 문제를 구체적으로 정의하는 것이다.

```text
무엇이 문제인가?
왜 중요한가?
언제부터 발생했는가?
어떤 대상에게 발생했는가?
문제를 해결하면 어떤 변화가 기대되는가?
```

예를 들어 단순히 "매출이 감소했다"라고 정의하는 것보다,

> 최근 3개월 동안 모바일 앱에서 유입된 신규 고객의 첫 구매 전환율이 하락하고 있다.

라고 정의하면 분석 대상, 기간, 고객군, 핵심 지표가 명확해진다.

### 2. 지표 설정

문제를 정의했다면 문제를 확인하기 위한 지표를 설정한다.

첫 구매 전환율 하락 문제라면 다음과 같은 지표를 확인할 수 있다.

- 모바일 앱 방문자 수
- 회원가입 전환율
- 상품 상세 페이지 조회율
- 장바구니 담기율
- 결제 시작률
- 결제 완료율
- 첫 구매 전환율

중요한 것은 **좋아 보이는 지표를 많이 모으는 것이 아니라 문제를 설명하는 데 필요한 지표를 선택하는 것**이다.

### 3. 데이터 수집 및 분석

지표를 정했다면 필요한 데이터를 수집하고 분석한다.

이때 다음을 확인해야 한다.

- 필요한 데이터가 존재하는가?
- 데이터가 정확하게 수집되고 있는가?
- 결측치와 이상치는 없는가?
- 기간별로 비교할 수 있는가?
- 고객군별로 나누어 볼 수 있는가?
- 채널별 차이가 있는가?
- 어떤 패턴이나 차이가 나타나는가?

특히 전체 평균만 보는 것보다 **채널별, 기기별, 고객군별, 날짜별로 나누어 보는 것**이 중요하다.

전체 지표에서는 보이지 않던 문제가 특정 구간에서 나타날 수 있기 때문이다.

### 4. 해석 및 의사결정

분석 결과를 확인한 다음에는 숫자의 의미를 현실적인 맥락에서 해석해야 한다.

예를 들어 결제 완료율이 특정 시점부터 급격하게 하락했다면 다음 가능성을 생각해볼 수 있다.

- 결제 시스템 오류
- 특정 브라우저나 기기 문제
- 배송비 또는 수수료 정책 변경
- 결제 화면 UI 변경
- 프로모션 종료

데이터는 의사결정의 근거를 제공하지만 최종 판단에는 **도메인 지식과 맥락에 대한 이해**도 필요하다.

### 5. 액션 실행

분석의 목적은 보고서를 만드는 것이 아니라 **실제 문제를 개선하는 것**이다.

예를 들어 결제 단계에서 이탈률이 높다면 다음과 같은 액션을 실행할 수 있다.

- 결제 오류 로그 확인
- 결제 화면 UI 개선
- 배송비 안내 문구 수정
- 간편결제 옵션 추가
- 특정 브라우저 오류 수정
- 결제 단계 A/B 테스트

액션은 구체적으로 정의해야 한다.

```text
무엇을
언제
누구와
어떤 기준으로
개선할 것인가?
```

### 6. 결과 검증

액션을 실행한 뒤에는 반드시 결과를 검증해야 한다.

다음 질문을 확인한다.

- 액션 이후 지표가 개선되었는가?
- 개선 폭이 기대한 수준인가?
- 다른 부작용은 없었는가?
- 특정 고객군에서만 효과가 있었는가?
- 일시적인 효과인가, 지속적인 효과인가?
- 추가로 개선해야 할 부분은 무엇인가?

액션 후 지표가 개선되었다면 해당 방법을 확대할 수 있다.

반대로 개선되지 않았다면 **처음 세운 가설이 틀렸을 가능성을 인정하고 다시 문제를 정의해야 한다.**

### 데이터 기반 의사결정의 핵심은 반복

데이터 기반 의사결정은 한 번에 정답을 찾는 과정이 아니다.

```text
문제 정의
  ↓
가설 설정
  ↓
데이터 확인
  ↓
액션 실행
  ↓
결과 확인
  ↓
다시 문제 정의
```

처음 세운 가설이 틀릴 수도 있고, 예상과 다른 분석 결과가 나올 수도 있다.

중요한 것은 실패하지 않는 것이 아니라 **데이터를 통해 빠르게 배우고 다음 의사결정을 더 나은 방향으로 만드는 것**이다.

---

## 실무 예시: 과제 제출률 개선

데이터 사이언스 교육 과정에서 과제 제출률이 낮아진 상황을 생각해보자.

### 문제 정의

> 3주차 이후 과제 제출률이 급격히 하락하고 있다.

### 지표 설정

- 주차별 과제 제출률
- 과제별 평균 소요 시간
- 과제 난이도 만족도
- 질문 게시판 질문 수
- 제출 마감 전 알림 확인율

### 데이터 분석

3주차 과제부터 제출률이 하락했고, 질문 게시판에 환경 설정 관련 질문이 많이 올라왔다.

이를 통해 과제 자체의 난이도보다 **과제를 시작하기 위한 환경 설정과 안내 부족**이 제출률 하락에 영향을 주었을 가능성을 생각할 수 있다.

### 액션

- 과제 시작 전 환경 설정 체크리스트 제공
- 자주 발생하는 오류 FAQ 작성
- 과제 풀이 예시 일부 제공
- 제출 마감 24시간 전 리마인드 발송

### 결과 검증

다음 과제에서 다음을 확인한다.

- 과제 제출률이 개선되었는가?
- 환경 설정 관련 질문이 감소했는가?
- 수강생 만족도가 변화했는가?
- 과제 완료 시간이 개선되었는가?

이처럼 데이터 분석은 **문제를 발견하는 것에서 끝나는 것이 아니라 실제 행동과 결과 개선으로 연결되어야 한다.**

## 오늘 배운 내용 정리

이번 학습을 통해 데이터 분석에서 가장 먼저 해야 할 일은 데이터를 보는 것이 아니라 **올바른 문제를 정의하는 것**이라는 점을 배웠다.

특히 기억할 내용은 다음과 같다.

- 문제 정의는 막연한 상황을 데이터로 확인할 수 있는 질문으로 바꾸는 과정이다.
- 좋은 분석 질문은 구체적이고, 데이터로 답할 수 있으며, 의사결정과 연결되어야 한다.
- 방문자 수, 활성 사용자 수, 전환율, 이탈률, 리텐션, 객단가 등의 서비스 지표는 각각 의미가 다르다.
- 하나의 지표만으로 서비스 상태를 판단하면 잘못된 결론을 내릴 수 있으므로 여러 지표를 사용자 행동 흐름에 따라 함께 봐야 한다.
- 데이터 기반 의사결정은 `문제 정의 → 지표 설정 → 데이터 분석 → 해석 및 의사결정 → 액션 → 검증`의 순환 과정이다.
- 분석의 목적은 데이터를 보는 것이 아니라 **실제 문제를 개선하는 것**이다.
- 액션을 실행한 후에는 반드시 결과를 검증하고, 결과에 따라 다시 문제 정의와 가설을 수정해야 한다.

### 한 줄 회고

> **좋은 데이터 분석은 많은 데이터를 보는 것이 아니라, 올바른 문제를 정의하고 데이터로 검증하여 실제 행동으로 연결하는 과정이다.**
