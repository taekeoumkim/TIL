## 1. 모델을 아는 것과 선택하는 것은 다르다

머신러닝에서는 다양한 모델의 사용법을 아는 것도 중요하지만, 실제 문제에 어떤 모델을 적용할지 근거를 들어 선택하는 능력이 더 중요하다.

실무에서는 다음 질문에 먼저 답해야 한다.

- 비즈니스가 해결하려는 문제는 무엇인가?
- 모델이 예측해야 할 값은 무엇인가?
- 각 클래스는 어떤 상태를 의미하는가?
- 어떤 종류의 예측 오류가 더 큰 비용을 만드는가?
- 모델의 예측 근거를 설명해야 하는가?
- 실제 서비스에서 요구하는 응답 속도와 자원 조건은 무엇인가?

모델의 Accuracy가 가장 높다는 이유만으로 최종 모델을 선택하면 실제 목적과 맞지 않을 수 있다. 먼저 문제를 올바르게 정의하고, 그 문제에 맞는 지표와 모델을 선택해야 한다.

```text
비즈니스 목표
    ↓
머신러닝 문제로 변환
    ↓
타깃과 클래스 정의
    ↓
오류 비용과 평가 지표 정의
    ↓
후보 모델 학습 및 비교
    ↓
성능과 운영 조건을 종합하여 최종 모델 선택
```

## 2. 비즈니스 문제를 분류 문제로 정의하기

비즈니스 목표는 그대로 머신러닝 모델에 입력할 수 없다. 목표를 모델이 학습할 수 있는 구체적인 예측 문제로 바꾸어야 한다.

예를 들어 구독 서비스 회사에 다음과 같은 목표가 있다고 가정한다.

> 다음 달에 서비스를 그만둘 가능성이 높은 고객에게 미리 혜택을 제공하자.

이 목표를 머신러닝 문제로 바꾸면 다음과 같다.

| 정의 항목 | 내용 |
|---|---|
| 문제 유형 | 이진 분류(Binary Classification) |
| 예측 타깃 | 다음 달 고객의 서비스 해지 여부 |
| 클래스 1 | 다음 달에 서비스를 해지한 고객 |
| 클래스 0 | 다음 달에도 서비스를 유지한 고객 |
| 주요 목적 | 실제 이탈 고객을 캠페인 대상에 포함 |
| 우선 지표 | Recall |

실제 이탈 고객을 최대한 놓치지 않는 것이 중요하므로, False Negative를 줄이는 방향으로 Recall을 우선 확인할 수 있다.

### 고객 이탈 모델의 Recall

```python
from sklearn.metrics import recall_score

# 1: 이탈, 0: 유지
y_true = [1, 1, 1, 0, 0, 1, 0, 0]
y_pred = [1, 1, 0, 0, 0, 1, 0, 1]

recall = recall_score(y_true, y_pred)

print("Recall:", recall)
```

실행 결과:

```text
Recall: 0.75
```

실제 이탈 고객은 4명이고, 모델은 그중 3명을 이탈 고객으로 찾아냈다.

$$
\mathrm{Recall}
=\frac{TP}{TP+FN}
=\frac{3}{4}
=0.75
$$

이처럼 같은 분류 문제라도 비즈니스에서 어떤 실수를 더 중요하게 보는지에 따라 우선적으로 확인할 평가 지표가 달라진다.

## 3. 문제 정의가 모델보다 먼저다

문제 정의가 잘못되면 성능이 높은 모델을 만들어도 비즈니스가 원하는 결과를 얻기 어렵다.

분류 문제를 정의할 때는 다음 순서로 생각할 수 있다.

### 1단계: 타깃 정의

무엇을 예측할 것인지 명확하게 정한다. 예측 시점과 기준 기간도 함께 정의해야 같은 타깃을 일관되게 만들 수 있다.

```text
모호한 목표: 이탈할 것 같은 고객 찾기

명확한 타깃: 기준일 이후 30일 안에 서비스를 해지했는가?
```

### 2단계: 클래스 정의

클래스 0과 1이 각각 무엇을 의미하는지 정한다. 일반적으로 비즈니스에서 탐지하고 싶은 대상을 Positive 클래스인 1로 정의한다.

```text
1 = 다음 달 해지 고객
0 = 다음 달 유지 고객
```

Positive 클래스가 무엇인지에 따라 TP, FP, FN, TN과 Precision·Recall의 해석이 달라진다.

### 3단계: 평가 지표 정의

비즈니스에서 어떤 오류가 더 위험하거나 비용이 큰지 판단하여 우선 지표를 정한다.

| 중요한 상황 | 오류 | 우선 고려 지표 |
|---|---|---|
| 실제 Positive를 놓치면 피해가 큼 | FN | Recall |
| 잘못된 Positive 판정의 비용이 큼 | FP | Precision |
| 두 오류의 균형이 중요함 | FP와 FN | F1-score |
| 클래스가 균형적이고 전체 정답 비율이 중요함 | 전체 오류 | Accuracy |

### 4단계: 모델 후보 선정

데이터의 특성, 해석 가능성, 예측 성능, 학습 및 추론 환경을 고려하여 비교할 모델을 선정한다.

이번 학습에서는 다음 세 모델을 후보로 비교한다.

- Logistic Regression
- Decision Tree
- Random Forest

## 4. 평가지표는 비즈니스 목적에서 결정된다

좋은 평가 지표는 가장 높은 값이 나오기 쉬운 지표가 아니라, 비즈니스 목적과 오류 비용을 잘 반영하는 지표이다.

### Recall이 중요한 경우

실제 Positive를 놓치는 False Negative의 비용이 큰 문제이다.

- 이탈 고객 탐지
- 질병 환자 선별
- 부정 거래 1차 탐지
- 불량품 검사

### Precision이 중요한 경우

Negative를 Positive로 잘못 판단하는 False Positive의 비용이 큰 문제이다.

- 정상 메일을 스팸으로 차단
- 정상 사용자를 부정 사용자로 제재
- 제한된 비용으로 소수 고객에게만 혜택 제공

### F1-score가 중요한 경우

Precision과 Recall이 모두 중요하거나 클래스가 불균형하여 Accuracy만으로 성능을 판단하기 어려운 경우 사용할 수 있다.

평가 지표를 정할 때는 숫자의 크기뿐 아니라 실제 운영에서 FP와 FN이 각각 어떤 결과를 만드는지 설명할 수 있어야 한다.

## 5. 모델 선택은 하나의 점수로 끝나지 않는다

금융회사에서 대출 연체 여부를 예측하는 세 모델의 Test Accuracy가 다음과 같다고 가정한다.

```python
model_scores = {
    "Logistic Regression": 0.84,
    "Decision Tree": 0.83,
    "Random Forest": 0.86,
}

for model, score in model_scores.items():
    print(f"{model}: {score:.2f}")
```

실행 결과:

```text
Logistic Regression: 0.84
Decision Tree: 0.83
Random Forest: 0.86
```

Accuracy만 보면 Random Forest가 가장 높다. 그러나 실제 대출 심사에서는 고객에게 왜 연체 위험이 높다고 판단했는지 설명해야 할 수 있다.

세 모델의 성능 차이는 최대 0.03이므로, 해석 가능성이 매우 중요한 환경에서는 Logistic Regression이나 Decision Tree를 선택할 수도 있다. 반대로 설명보다 예측 성능이 중요하고 충분한 데이터와 컴퓨팅 자원이 있다면 Random Forest를 선택할 수 있다.

즉, 모델 선택은 다음 요소를 함께 고려하는 의사결정이다.

- 예측 성능
- 해석 가능성
- 추론 속도
- 학습 시간
- 모델 크기
- 데이터의 양과 복잡도
- 사용할 수 있는 컴퓨팅 자원
- 운영 및 유지보수 편의성

## 6. 세 가지 분류 모델 비교

| 모델 | 해석 가능성 | 주요 특징 | 적합한 상황 |
|---|---|---|---|
| Logistic Regression | 높음 | 입력 Feature와 예측 결과의 관계를 비교적 해석하기 쉬움 | 각 Feature가 결과에 미치는 방향과 영향을 설명해야 할 때 |
| Decision Tree | 매우 높음 | 질문과 분기 구조로 예측 과정을 직관적으로 표현 | 개별 예측의 판단 경로를 규칙 형태로 설명해야 할 때 |
| Random Forest | 중간 | 여러 결정트리를 결합하여 안정성과 일반화 성능 향상 | 데이터 관계가 복잡하고 예측 성능이 더 중요할 때 |

### Logistic Regression

입력 Feature의 선형결합을 확률로 변환하여 클래스를 예측한다.

장점:

- 구조가 비교적 단순하다.
- 학습과 예측이 빠른 편이다.
- 계수를 통해 각 Feature와 예측 결과의 관계를 살펴볼 수 있다.
- 기준 모델(Baseline)로 사용하기 좋다.

고려할 점:

- 데이터 관계가 복잡하고 비선형적이면 충분한 성능을 내지 못할 수 있다.
- 계수의 올바른 비교를 위해 데이터 전처리와 Feature 스케일을 고려해야 한다.

### Decision Tree

Feature와 기준값에 대한 질문을 반복하여 데이터를 나눈다.

장점:

- 예측 경로가 직관적이다.
- 비선형적인 관계를 표현할 수 있다.
- 별도의 Feature Scaling이 필요하지 않은 경우가 많다.

고려할 점:

- 트리가 너무 깊어지면 학습 데이터에 과대적합되기 쉽다.
- 데이터가 조금 바뀌어도 트리 구조가 크게 달라질 수 있다.

### Random Forest

서로 다른 여러 결정트리의 예측을 결합한다.

장점:

- 단일 결정트리보다 안정적인 예측을 만드는 경우가 많다.
- 복잡하고 비선형적인 관계를 학습할 수 있다.
- 단일 결정트리보다 과대적합에 강한 편이다.

고려할 점:

- 여러 트리를 사용하므로 학습·추론 비용과 모델 크기가 증가한다.
- 하나의 Decision Tree보다 전체 판단 과정을 설명하기 어렵다.

## 7. 성능 외의 모델 선택 기준

### 해석 가능성

대출 심사, 보험, 인사처럼 모델의 판단이 사람에게 직접 영향을 미치는 문제에서는 예측 근거를 설명하는 능력이 중요할 수 있다.

성능 차이가 작다면 더 단순하고 설명하기 쉬운 모델이 실제 운영에 적합할 수 있다.

### 추론 속도

고객 문의 자동 분류처럼 짧은 시간에 많은 요청을 처리해야 한다면 모델 한 건의 예측 시간이 중요하다. 정확도가 조금 높더라도 응답이 지나치게 느리면 서비스 요구사항을 충족하지 못할 수 있다.

### 데이터의 양과 복잡도

데이터가 비교적 단순하거나 적다면 단순한 모델이 충분한 성능을 낼 수 있다. 복잡한 모델은 일반적으로 더 많은 데이터가 있어야 안정적으로 학습되는 경우가 많다.

### 컴퓨팅 자원

학습 서버의 CPU·메모리, 서비스 환경의 지연 시간과 비용을 고려해야 한다. 여러 트리를 사용하는 Random Forest는 단일 Logistic Regression이나 Decision Tree보다 더 많은 자원을 사용할 수 있다.

### 운영과 유지보수

모델을 주기적으로 재학습하고 배포해야 한다면 학습 시간, 버전 관리, 모니터링과 장애 대응의 편의성도 중요하다.

```text
검증 성능이 비슷함
    ↓
해석 가능성·속도·비용·운영 조건 비교
    ↓
목표를 만족하는 가장 적절한 복잡도의 모델 선택
```

가장 복잡한 모델이나 가장 높은 점수의 모델이 항상 최선은 아니다.

## 8. 높은 Accuracy의 함정

고객 100명 중 실제 이탈 고객이 5명이고 유지 고객이 95명이라고 가정한다. 모델이 모든 고객을 유지 고객으로 예측하면 Accuracy는 95%이다.

```python
from sklearn.metrics import accuracy_score, recall_score

y_true = [1] * 5 + [0] * 95
y_pred = [0] * 100

accuracy = accuracy_score(y_true, y_pred)
recall = recall_score(y_true, y_pred)

print("Accuracy:", accuracy)
print("Recall:", recall)
```

실행 결과:

```text
Accuracy: 0.95
Recall: 0.0
```

모델은 전체 100명 중 유지 고객 95명을 맞혔으므로 Accuracy가 높다. 하지만 실제 이탈 고객 5명은 한 명도 찾지 못했다.

$$
\mathrm{Accuracy}=\frac{95}{100}=0.95
$$

$$
\mathrm{Recall}=\frac{0}{0+5}=0
$$

이 모델은 이탈 방지 캠페인이라는 목적을 전혀 달성하지 못한다. 따라서 Accuracy가 높다는 사실만으로 좋은 모델이라고 판단해서는 안 된다.

## 9. 데이터 불균형

데이터 불균형은 특정 클래스의 데이터가 다른 클래스보다 매우 적은 상태이다.

고객 이탈, 부정 거래, 질병 진단, 불량품 탐지에서는 일반적으로 Positive 데이터가 Negative 데이터보다 훨씬 적을 수 있다.

### 확인해야 할 사항

- 각 클래스의 데이터 개수와 비율
- Confusion Matrix의 TP, FP, FN, TN
- Positive 클래스에 대한 Precision과 Recall
- Precision과 Recall의 균형을 나타내는 F1-score
- 비즈니스에서 중요한 오류 유형

```python
print(y.value_counts())
print(y.value_counts(normalize=True))
```

`value_counts()`는 클래스별 개수를 확인하고, `normalize=True`를 사용하면 전체에서 각 클래스가 차지하는 비율을 확인할 수 있다.

### 개선 방향

- 문제에 맞는 Precision, Recall, F1-score를 사용한다.
- 데이터 수집 단계에서 소수 클래스 데이터를 더 확보한다.
- 학습 데이터의 클래스 균형을 조정하는 방법을 검토한다.
- 모델의 클래스 가중치 설정을 검토한다.
- 분류 Threshold를 비즈니스 목적에 맞게 조정한다.

평가용 Test 데이터의 실제 클래스 비율은 유지해야 공정한 일반화 성능을 확인할 수 있다.

## 10. 과대적합(Overfitting)

과대적합은 모델이 학습 데이터에 지나치게 맞춰져 Train 성능은 높지만 새로운 데이터의 성능은 낮은 상태이다.

```text
Train 성능은 매우 높음
Test 성능은 크게 낮음
→ Overfitting 의심
```

모델을 평가할 때는 Train 성능과 Test 또는 Validation 성능을 함께 확인해야 한다.

### 개선 방향

- 모델의 복잡도를 낮춘다.
- 더 많은 학습 데이터를 확보한다.
- 정규화(Regularization)를 적용하거나 강도를 조절한다.
- 하이퍼파라미터를 교차검증으로 조정한다.
- 불필요하거나 노이즈가 많은 Feature를 점검한다.

Decision Tree라면 다음 하이퍼파라미터로 복잡도를 제한할 수 있다.

- `max_depth`
- `min_samples_split`
- `min_samples_leaf`

Train 성능이 조금 낮아지더라도 Test 성능이 높아지고 두 성능의 차이가 줄어든다면 새로운 데이터에 더 잘 일반화하는 모델일 수 있다.

---

## 11. 해석이 어려운 모델

예측 성능은 높지만 판단 근거를 설명하기 어려운 모델이 비즈니스 요구사항에 맞지 않을 수 있다.

특히 대출 거절이나 지원 대상 제외처럼 사용자에게 판단 기준을 설명해야 하는 경우에는 해석 가능성을 모델 선택 조건으로 포함해야 한다.

### 개선 방향

- Logistic Regression이나 Decision Tree처럼 비교적 해석하기 쉬운 모델을 후보에 포함한다.
- 복잡한 모델이 반드시 필요하다면 모델 해석 기법의 활용을 검토한다.
- 전체 모델의 성능과 개별 예측의 설명 가능성을 별도로 평가한다.
- 성능 차이와 설명 가능성 사이의 Trade-off를 이해관계자와 합의한다.

해석 가능성은 모델 학습이 끝난 뒤 추가로 생각하는 요소가 아니라, 문제를 정의하고 모델 후보를 정하는 단계부터 고려해야 한다.

---

## 12. 모델의 한계와 개선 방향

| 한계 상황 | 확인할 내용 | 개선 방향 |
|---|---|---|
| 데이터 불균형 | 클래스 비율, Confusion Matrix, Recall, F1-score | 적절한 지표 사용, 소수 클래스 데이터 확보, 클래스 균형 조정 |
| Train 성능은 높고 Test 성능은 낮음 | Train-Test 성능 차이 | 복잡도 축소, 데이터 추가, 정규화, 하이퍼파라미터 조정 |
| 성능은 좋지만 해석이 어려움 | 설명 의무와 사용자 영향 | 해석 가능한 모델 선택 또는 모델 해석 기법 활용 |
| 추론 시간이 너무 김 | 요청량, 응답 지연, 자원 사용량 | 더 단순한 모델 검토, 모델 및 실행 환경 최적화 |
| 성능 차이가 매우 작음 | 지표의 변동성과 운영 조건 | 해석성·속도·비용·유지보수를 함께 비교 |

어떤 모델도 모든 문제에서 항상 가장 좋은 성능을 보이지 않는다. 모델의 약점을 이해해야 다음 개선 실험을 설계할 수 있다.

---

## 13. 실무적인 모델 비교 절차

### 1. 비즈니스 목표 정리

모델의 예측을 누가, 언제, 어떤 행동에 사용할지 정한다.

### 2. 타깃과 클래스 정의

예측 시점, 관찰 기간, 클래스 0과 1의 의미를 명확하게 정한다.

### 3. 오류 비용과 평가 지표 선택

FP와 FN이 만드는 실제 피해를 비교하고 Primary Metric을 결정한다.

### 4. 데이터 분할과 클래스 비율 확인

Train, Validation, Test를 분리하고 각 집합의 클래스 분포를 점검한다.

### 5. 기준 모델 학습

해석하기 쉽고 빠른 Logistic Regression 등을 Baseline으로 학습한다.

### 6. 여러 후보를 같은 조건에서 비교

같은 데이터 분할과 평가 지표를 사용해 Decision Tree, Random Forest 등을 비교한다.

### 7. 한계와 운영 조건 점검

과대적합, 불균형 데이터 성능, 추론 시간, 모델 크기, 설명 가능성을 확인한다.

### 8. 최종 모델 선택

검증 성능과 운영 요구사항을 함께 만족하는 모델을 선택하고, 마지막에 Test Set으로 일반화 성능을 확인한다.

```text
문제와 행동 정의
    ↓
타깃·클래스·지표 정의
    ↓
동일 조건에서 후보 모델 비교
    ↓
불균형·과대적합·해석성·속도 점검
    ↓
비즈니스 목표에 가장 적합한 모델 선택
```

## 14. 핵심 용어 정리

| 용어 | 의미 |
|---|---|
| Business Problem | 조직이나 서비스가 실제로 해결하려는 문제 |
| Target | 모델이 예측해야 하는 정답 변수 |
| Positive Class | 모델이 중점적으로 탐지하려는 클래스 |
| Evaluation Metric | 모델의 성능을 문제 목적에 맞게 측정하는 기준 |
| Model Selection | 성능과 제약 조건을 비교하여 최종 모델을 선택하는 과정 |
| Interpretability | 모델이 왜 특정 예측을 했는지 사람이 이해하고 설명할 수 있는 정도 |
| Inference Time | 학습된 모델이 새로운 입력의 예측을 만드는 데 걸리는 시간 |
| Data Imbalance | 클래스별 데이터 수나 비율이 크게 다른 상태 |
| Overfitting | 학습 데이터에는 잘 맞지만 새로운 데이터에는 성능이 낮은 상태 |
| Generalization | 모델이 학습하지 않은 새로운 데이터에서도 성능을 유지하는 능력 |

## 15. 오늘 배운 내용 정리

### 문제 정의

- 비즈니스 목표를 바로 모델에 입력할 수 없으므로 명확한 머신러닝 문제로 바꿔야 한다.
- 무엇을 예측할지 타깃을 정의하고 클래스 0과 1의 의미를 정해야 한다.
- 문제 정의가 잘못되면 성능이 좋은 모델도 원하는 결과를 만들기 어렵다.

### 평가 지표

- 실제 Positive를 놓치지 않는 것이 중요하면 Recall을 우선 확인한다.
- 잘못된 Positive 판정의 비용이 크면 Precision을 우선 확인한다.
- 클래스가 불균형하면 Accuracy만으로 모델을 판단하지 않는다.
- 평가 지표는 비즈니스의 오류 비용과 연결하여 선택한다.

### 모델 선택

- 모델은 하나의 성능 점수만으로 선택하지 않는다.
- 해석 가능성, 추론 속도, 데이터 양, 컴퓨팅 자원과 운영 조건을 함께 고려한다.
- Logistic Regression과 Decision Tree는 비교적 해석하기 쉽다.
- Random Forest는 복잡한 관계를 학습하고 안정적인 성능을 보일 수 있지만 해석과 비용 측면을 함께 검토해야 한다.

### 한계와 개선

- 높은 Accuracy가 항상 좋은 모델을 의미하지는 않는다.
- Train과 Test 성능 차이가 크면 Overfitting을 의심한다.
- 모델의 한계를 찾은 뒤 데이터, 복잡도, 정규화, 하이퍼파라미터와 평가 방식을 개선한다.

### 전체 흐름

```text
비즈니스 문제 이해
    ↓
타깃과 클래스 정의
    ↓
오류 비용에 맞는 지표 선택
    ↓
동일한 조건에서 여러 모델 비교
    ↓
성능·해석성·속도·자원 종합 판단
    ↓
한계 점검과 개선
```

## 16. 느낀 점

오늘은 머신러닝 모델의 사용법을 아는 것과 실제 문제에 적합한 모델을 선택하는 것은 다른 능력이라는 점을 배웠다. 모델을 학습하기 전에 비즈니스 목표를 타깃과 클래스로 명확하게 바꾸고, 어떤 오류가 더 중요한지 결정해야 한다는 순서가 가장 중요하게 느껴졌다.

고객 이탈 문제에서는 실제 이탈 고객을 놓치지 않는 것이 캠페인의 목적이므로 Accuracy보다 Recall이 더 중요한 지표가 될 수 있었다. 같은 모델 결과라도 비즈니스가 False Positive와 False Negative 중 어느 쪽을 더 큰 비용으로 보는지에 따라 평가가 달라진다는 것을 이해했다.

또한 Accuracy가 가장 높은 모델이 항상 최종 선택은 아니라는 점이 인상적이었다. 대출 심사처럼 판단 근거를 설명해야 하는 환경에서는 성능이 조금 낮더라도 Logistic Regression이나 Decision Tree가 더 적합할 수 있고, 복잡한 패턴의 예측 성능이 중요하다면 Random Forest를 고려할 수 있다.

클래스가 불균형한 이탈 데이터에서 모든 고객을 유지로 예측해도 Accuracy가 95%가 되는 예제를 통해, 높은 점수 하나만 보면 모델의 치명적인 실패를 놓칠 수 있다는 점도 확인했다. 앞으로 분류 모델을 평가할 때는 먼저 클래스 비율과 Confusion Matrix를 확인하고, 문제에 맞는 Precision, Recall, F1-score를 함께 사용해야겠다.

향후 프로젝트에서는 모델별 점수만 표로 나열하지 않고, 타깃 정의와 지표 선택 이유, 해석 가능성, 추론 속도, 자원 제약, 발견된 한계와 개선 실험까지 연결하여 모델 선택의 근거를 설명하는 습관을 들여야겠다.
