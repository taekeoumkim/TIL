# 2026-09-09 실행계획(EXPLAIN) 읽는 법

## 학습 목표

- `EXPLAIN`과 `EXPLAIN ANALYZE`의 차이를 설명할 수 있다.
- 실행계획에서 데이터 접근 방식과 주요 항목을 해석할 수 있다.
- `Seq Scan`, `Index Scan`, `Index Only Scan`의 차이를 이해할 수 있다.
- `cost`, 예상 행 수, 실제 행 수를 비교하여 옵티마이저의 예측을 점검할 수 있다.
- 실행계획 트리를 실제 데이터 처리 순서에 맞게 읽을 수 있다.
- 실행계획에서 성능 병목의 단서를 찾을 수 있다.

---

## 1. 실행계획을 확인하는 이유

SQL을 작성하면 옵티마이저는 여러 실행 방법을 비교한 뒤 하나의 실행계획을 선택한다. PostgreSQL에서는 `EXPLAIN` 명령으로 옵티마이저가 선택한 계획을 확인할 수 있다.

실행계획을 살펴보면 다음과 같은 내용을 알 수 있다.

- 테이블을 어떤 방식으로 읽는가?
- 인덱스를 사용하는가?
- 각 단계에서 몇 개의 행을 처리할 것으로 예상하는가?
- 여러 테이블을 어떤 순서와 방법으로 결합하는가?
- 실제 실행 시 어느 단계에서 많은 시간과 데이터를 처리하는가?

따라서 쿼리가 느릴 때는 SQL 문장만 보는 것이 아니라 실행계획을 통해 데이터베이스가 실제로 선택한 처리 방법을 확인해야 한다.

---

## 2. EXPLAIN과 EXPLAIN ANALYZE

`EXPLAIN`과 `EXPLAIN ANALYZE`는 모두 실행계획을 보여주지만, 쿼리를 실제로 실행하는지에 차이가 있다.

| 명령어 | 쿼리 실제 실행 | 확인할 수 있는 내용 |
|---|---:|---|
| `EXPLAIN` | 아니요 | 옵티마이저가 세운 실행계획과 예상 비용·행 수 |
| `EXPLAIN ANALYZE` | 예 | 예상 실행계획과 실제 소요 시간·처리 행 수 |

배송 경로에 비유하면 `EXPLAIN`은 지도를 보고 예상 경로를 세우는 것이고, `EXPLAIN ANALYZE`는 실제로 운행한 뒤 시간과 결과를 측정하는 것이다.

### EXPLAIN

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 100;
```

실행계획 예시:

```text
Gather  (cost=1000.00..7328.27 rows=6 width=32)
  Workers Planned: 2
  ->  Parallel Seq Scan on orders
        (cost=0.00..6327.67 rows=2 width=32)
        Filter: (customer_id = 100)
```

`EXPLAIN`의 `cost`와 `rows`는 옵티마이저가 통계정보를 바탕으로 계산한 예상값이다. 쿼리를 실제로 실행한 결과가 아니다.

### EXPLAIN ANALYZE

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 100;
```

실행계획 예시:

```text
Gather  (cost=1000.00..7328.27 rows=6 width=32)
        (actual time=4.420..120.775 rows=6 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  ->  Parallel Seq Scan on orders
        (cost=0.00..6327.67 rows=2 width=32)
        (actual time=1.371..5.402 rows=2 loops=3)
        Filter: (customer_id = 100)
        Rows Removed by Filter: 166665
Planning Time: 0.052 ms
Execution Time: 120.792 ms
```

`EXPLAIN ANALYZE`에는 `actual time`, 실제 `rows`, `loops`, 전체 실행 시간 등이 추가된다. 이를 통해 옵티마이저의 예상과 실제 실행 결과가 얼마나 일치하는지 비교할 수 있다.

> `EXPLAIN ANALYZE`는 쿼리를 실제로 실행한다. 데이터 변경 쿼리에 사용할 때는 실제 데이터가 변경될 수 있으므로 주의해야 한다.

## 3. 실행계획의 주요 항목

실행계획에 반복해서 등장하는 주요 항목은 다음과 같다.

| 항목 | 의미 |
|---|---|
| `cost=a..b` | 첫 행을 반환하기까지의 시작 비용 `a`와 모든 행을 반환하기까지의 총 비용 `b` |
| `rows` | 해당 노드가 반환할 것으로 옵티마이저가 예상한 행 수 |
| `width` | 한 행의 예상 평균 크기(Byte) |
| `actual time=a..b` | 실제 첫 행 반환 시점과 모든 행 반환 완료 시점 |
| `actual rows` | 해당 노드가 실제로 반환한 행 수 |
| `loops` | 해당 노드가 반복 실행된 횟수 |
| `Filter` | 데이터를 읽은 뒤 적용한 필터 조건 |
| `Rows Removed by Filter` | 필터 조건을 만족하지 않아 제외된 행 수 |
| `Planning Time` | 실행계획을 만드는 데 걸린 시간 |
| `Execution Time` | 쿼리 전체를 실제로 실행하는 데 걸린 시간 |

`cost`는 밀리초(ms)가 아니다. 옵티마이저가 여러 실행계획의 효율을 비교하기 위해 사용하는 상대적인 비용 값이다. 실제 시간은 `EXPLAIN ANALYZE`의 `actual time`과 `Execution Time`에서 확인해야 한다.

## 4. Seq Scan(Full Scan)

`Seq Scan`은 테이블의 데이터를 순차적으로 읽으면서 조건에 맞는 행을 찾는 방식이다. 일반적으로 Full Scan이라고 부르는 접근 방식에 해당한다.

```sql
EXPLAIN
SELECT *
FROM customers
WHERE customer_id = 100;
```

인덱스를 사용하지 않는 실행계획 예시:

```text
Seq Scan on customers  (cost=0.00..4192.00 rows=1 width=102)
  Filter: (customer_id = 100)
```

특정 행 하나만 찾는데 `Seq Scan`이 수행된다면 많은 데이터를 읽을 수 있다. 그러나 조회 대상이 테이블 전체의 상당 부분이라면 여러 번 인덱스를 거쳐 테이블에 접근하는 것보다 순차적으로 읽는 편이 더 효율적일 수 있다.

따라서 `Seq Scan`이 보인다는 이유만으로 항상 잘못된 실행계획이라고 판단해서는 안 된다.

---

## 5. Index Scan

`Index Scan`은 인덱스에서 조건에 맞는 값의 위치를 찾은 뒤, 해당 위치의 실제 테이블 데이터에 접근하는 방식이다.

```text
Index Scan using idx_customers_customer_id on customers
  (cost=0.29..8.31 rows=1 width=80)
  Index Cond: (customer_id = 100)
```

조회 대상이 전체 데이터 중 소수이고 조건에 적절한 인덱스가 있을 때 유리할 수 있다.

```text
인덱스에서 조건에 맞는 위치 탐색
    ↓
해당 위치의 테이블 행에 접근
    ↓
결과 반환
```

다만 인덱스가 존재한다고 해서 옵티마이저가 항상 `Index Scan`을 선택하는 것은 아니다. 조회 범위가 넓으면 `Seq Scan`이 더 효율적이라고 판단할 수 있다.

---

## 6. Index Only Scan

`Index Only Scan`은 쿼리에 필요한 정보가 인덱스에 모두 포함되어 있고 테이블 본문을 추가로 확인할 필요가 없을 때, 주로 인덱스만 읽어 결과를 만드는 방식이다.

```text
Index Only Scan using idx_customers_customer_id on customers
  (cost=0.29..4.31 rows=1 width=4)
  Index Cond: (customer_id = 100)
```

`Index Scan`은 인덱스로 위치를 찾은 뒤 테이블 데이터까지 읽는 반면, `Index Only Scan`은 조건이 맞으면 인덱스에 포함된 정보만으로 처리를 마칠 수 있다는 차이가 있다.

### 스캔 방식 비교

| 스캔 방식 | 데이터 접근 범위 | 유리한 상황 |
|---|---|---|
| `Seq Scan` | 테이블을 순차적으로 읽음 | 조회 대상이 전체 데이터의 상당 부분일 때 |
| `Index Scan` | 인덱스로 위치를 찾은 뒤 테이블에 접근 | 조회 대상이 소수이고 적절한 인덱스가 있을 때 |
| `Index Only Scan` | 필요한 데이터를 주로 인덱스에서 조회 | 조회에 필요한 컬럼이 인덱스에 포함되어 있을 때 |

스캔 방식은 무조건적인 우열 관계가 아니라 조회 범위와 데이터 상태에 따라 선택되는 접근 방법이다.

## 7. cost 읽는 법

`cost`는 다음과 같이 두 개의 숫자로 표시된다.

```text
cost=0.00..10000.80
```

| 값 | 의미 |
|---|---|
| `0.00` | 첫 번째 행을 반환하기 시작할 때까지의 시작 비용 |
| `10000.80` | 해당 노드가 모든 결과를 반환하기까지의 총 비용 |

비용은 실제 실행 시간이 아니라 옵티마이저 내부의 상대적인 계산 단위이다. 따라서 `cost=10000`을 실행 시간 10초 또는 10,000ms로 해석하면 안 된다.

비용은 후보 실행계획끼리 비교할 때 사용한다.

```text
후보 실행계획 생성
    ↓
각 계획의 예상 비용 계산
    ↓
비용이 낮을 것으로 판단되는 계획 선택
```

## 8. 예상 행 수와 실제 행 수 비교

옵티마이저는 통계정보를 바탕으로 각 실행 단계에서 처리할 행 수를 예상한다. `EXPLAIN ANALYZE`를 사용하면 예상 행 수와 실제 행 수를 비교할 수 있다.

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE order_date > '2016-01-01';
```

실행계획 예시:

```text
Seq Scan on orders
  (cost=0.00..10000.80 rows=167915 width=32)
  (actual time=0.010..22.822 rows=499845 loops=1)
  Filter: (order_date > '2016-01-01'::date)
  Rows Removed by Filter: 155
Planning Time: 0.045 ms
Execution Time: 31.142 ms
```

이 결과를 해석하면 다음과 같다.

| 확인 항목 | 값 | 해석 |
|---|---:|---|
| 예상 행 수 | 167,915 | 옵티마이저가 조건을 만족할 것으로 예상한 행 수 |
| 실제 행 수 | 499,845 | 실행 결과 실제로 반환된 행 수 |
| 필터로 제외된 행 수 | 155 | 조건을 만족하지 않아 제거된 행 수 |
| 전체 행 수 | 500,000 | 실제 반환 행과 필터 제거 행을 더한 수 |

옵티마이저는 약 167,915개를 예상했지만 실제로는 499,845개를 반환했다. 예상과 실제의 차이가 크면 옵티마이저가 실제 데이터 분포를 충분히 반영하지 못했을 가능성이 있다.

이 경우 다음 항목을 점검할 수 있다.

- 통계정보가 현재 데이터 상태를 반영하는가?
- 특정 값이나 범위에 데이터가 편중되어 있는가?
- 예상 행 수의 오차가 비효율적인 실행계획 선택으로 이어졌는가?

예상 행 수가 부정확하면 옵티마이저가 스캔 방식이나 조인 방식 등을 잘못 판단할 수 있으므로 중요한 점검 항목이다.

## 9. 실행계획은 트리 구조로 읽는다

여러 테이블을 조인하는 쿼리의 실행계획은 트리 구조로 표현된다.

```sql
EXPLAIN
SELECT o.order_id,
       c.first_name,
       c.last_name
FROM orders AS o
JOIN customers AS c
  ON o.customer_id = c.customer_id;
```

실행계획 예시:

```text
Hash Join  (cost=5192.00..20859.92 rows=503744 width=18)
  Hash Cond: (o.customer_id = c.customer_id)
  ->  Seq Scan on orders o
        (cost=0.00..8741.44 rows=503744 width=8)
  ->  Hash
        (cost=3942.00..3942.00 rows=100000 width=18)
        ->  Seq Scan on customers c
              (cost=0.00..3942.00 rows=100000 width=18)
```

실행계획을 단순히 위에서 아래로 읽으면 실제 처리 순서를 이해하기 어렵다. 가장 안쪽이자 아래쪽에 있는 자식 노드부터 읽고, 그 결과가 상위 노드로 어떻게 전달되는지 따라가야 한다.

### 처리 순서

1. `Seq Scan on customers c`
   - `customers` 테이블을 순차적으로 읽는다.
2. `Hash`
   - 읽어 온 고객 데이터를 이용해 조인에 사용할 해시 구조를 만든다.
3. `Seq Scan on orders o`
   - 다른 쪽에서 `orders` 테이블을 순차적으로 읽는다.
4. `Hash Join`
   - `orders.customer_id`와 `customers.customer_id`를 비교하여 두 결과를 결합한다.

```text
customers → Seq Scan → Hash ──┐
                              ├─→ Hash Join
orders    → Seq Scan ─────────┘
```

각 노드는 하위 노드가 만든 결과를 입력으로 받아 다음 작업을 수행한다. 따라서 가장 깊은 스캔 노드부터 시작하여 상위 노드 방향으로 읽는 것이 핵심이다.

## 10. 실행계획에서 병목 찾는 순서

실행계획을 처음부터 모든 숫자와 용어로 해석하려 하기보다 다음 순서로 확인하면 이해하기 쉽다.

### 1단계: 데이터 접근 방식 확인

- 어떤 테이블에서 `Seq Scan`이 발생했는가?
- `Index Scan` 또는 `Index Only Scan`을 사용하는가?
- 조회 범위를 고려했을 때 선택된 스캔 방식이 자연스러운가?

### 2단계: 처리 행 수 확인

- 각 노드의 예상 `rows`는 얼마인가?
- `EXPLAIN ANALYZE`의 실제 `rows`와 차이가 큰가?
- `Rows Removed by Filter`가 지나치게 많지는 않은가?

### 3단계: 비용과 실제 시간 확인

- 총 비용이 큰 노드는 어디인가?
- 실제 시간이 많이 걸린 노드는 어디인가?
- 해당 노드가 여러 번 반복 실행되지는 않았는가?

### 4단계: 트리의 처리 흐름 확인

- 가장 안쪽의 스캔부터 어떤 순서로 결과가 전달되는가?
- 어느 단계에서 많은 데이터가 상위 노드로 전달되는가?
- 조인 전에 불필요하게 많은 행을 읽고 있지는 않은가?

```text
스캔 방식
    ↓
예상 행 수와 실제 행 수
    ↓
비용과 실제 시간
    ↓
하위 노드에서 상위 노드로 이어지는 처리 흐름
```

## 11. 실행계획 해석 시 주의할 점

- `cost`를 실제 실행 시간으로 해석하지 않는다.
- 인덱스가 있다고 해서 `Index Scan`이 항상 더 좋은 것은 아니다.
- `Seq Scan`이라는 이유만으로 무조건 성능 문제라고 판단하지 않는다.
- 예상 행 수와 실제 행 수는 서로 다른 값이므로 구분한다.
- 실행계획은 위에서 아래가 아니라 가장 안쪽의 하위 노드부터 읽는다.
- 실제 성능을 확인하려면 `EXPLAIN ANALYZE`가 필요하지만, 쿼리가 실제로 실행된다는 점에 주의한다.
- 한 항목만 보고 결론을 내리지 않고 스캔 방식, 행 수, 비용, 실제 시간, 반복 횟수를 함께 살펴본다.

---

## 12. 핵심 용어 정리

| 용어 | 의미 |
|---|---|
| `EXPLAIN` | 쿼리를 실행하지 않고 옵티마이저의 예상 실행계획을 확인하는 명령 |
| `EXPLAIN ANALYZE` | 쿼리를 실제로 실행하고 예상값과 실제 측정값을 함께 확인하는 명령 |
| `Seq Scan` | 테이블을 순차적으로 읽으며 필요한 행을 찾는 방식 |
| `Index Scan` | 인덱스로 행 위치를 찾은 뒤 테이블 데이터를 읽는 방식 |
| `Index Only Scan` | 조건이 맞으면 필요한 데이터를 주로 인덱스만으로 읽는 방식 |
| `cost` | 옵티마이저가 실행계획을 비교할 때 사용하는 상대적인 예상 비용 |
| Estimated Rows | 옵티마이저가 통계정보를 바탕으로 예상한 반환 행 수 |
| Actual Rows | 실행 과정에서 실제로 반환된 행 수 |
| `Rows Removed by Filter` | 필터 조건을 만족하지 않아 제외된 행 수 |
| Execution Plan Tree | 데이터 접근과 조인 등 여러 실행 단계를 계층적으로 나타낸 구조 |

## 13. 오늘 배운 내용 정리

### EXPLAIN과 EXPLAIN ANALYZE

- `EXPLAIN`은 쿼리를 실제로 실행하지 않고 예상 실행계획을 보여준다.
- `EXPLAIN ANALYZE`는 쿼리를 실제로 실행하고 실제 시간과 행 수를 함께 보여준다.
- 예상과 실제의 차이를 비교하려면 `EXPLAIN ANALYZE`를 사용한다.
- `cost`는 실제 시간(ms)이 아니라 실행계획 비교를 위한 상대적인 비용이다.

### 스캔 방식

- `Seq Scan`은 테이블을 순차적으로 읽는다.
- `Index Scan`은 인덱스로 위치를 찾은 뒤 테이블 데이터에 접근한다.
- `Index Only Scan`은 조건이 맞으면 필요한 데이터를 주로 인덱스만으로 처리한다.
- 인덱스가 있더라도 조회 범위가 넓으면 `Seq Scan`이 선택될 수 있다.

### 비용과 행 수

- `cost=시작 비용..총 비용` 형태로 표시된다.
- `rows`는 옵티마이저가 예상한 반환 행 수이다.
- `actual rows`는 실제로 반환된 행 수이다.
- 예상 행 수와 실제 행 수의 차이가 크면 통계정보와 데이터 분포를 점검할 수 있다.
- `Rows Removed by Filter`로 조건에 의해 제외된 데이터의 양을 확인할 수 있다.

### 실행계획 트리

- 실행계획은 가장 안쪽의 하위 노드부터 읽는다.
- 스캔 결과가 해시 생성이나 조인 같은 상위 노드로 전달되는 흐름을 따라간다.
- 병목을 찾을 때는 스캔 방식, 처리 행 수, 비용, 실제 시간, 반복 횟수를 함께 확인한다.

## 한 문장 정리

> 실행계획은 데이터베이스가 SQL을 어떻게 처리하는지 보여주며, 하위 스캔부터 비용·예상 행 수·실제 행 수를 따라가면 성능 병목의 원인을 찾을 수 있다.
