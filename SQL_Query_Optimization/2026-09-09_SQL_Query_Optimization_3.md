# 2026-09-09 인덱스 구조와 동작 원리

## 학습 목표

- 인덱스가 필요한 이유를 설명할 수 있다.
- B-Tree 인덱스의 구조와 탐색 원리를 이해할 수 있다.
- 인덱스가 검색 범위를 줄여 조회 성능을 높이는 과정을 설명할 수 있다.
- PostgreSQL에서 인덱스를 생성하고 삭제할 수 있다.
- 인덱스가 조회 성능과 쓰기 성능에 미치는 영향을 이해할 수 있다.
- 조회 조건과 데이터 변경 빈도를 고려하여 인덱스 생성 여부를 판단할 수 있다.

---

## 1. 인덱스가 필요한 이유

테이블의 데이터가 적을 때는 원하는 값을 찾는 데 큰 시간이 걸리지 않을 수 있다. 그러나 데이터가 수십만 건, 수백만 건으로 늘어나면 같은 `SELECT` 쿼리라도 응답 속도가 눈에 띄게 느려질 수 있다.

인덱스가 없는 테이블에서 특정 값을 찾으려면 PostgreSQL이 많은 행을 처음부터 순서대로 확인하는 `Seq Scan`을 사용할 수 있다.

```text
[10] → [25] → [37] → [51] → [83] → ... → [300]
  ↑      ↑      ↑      ↑      ↑               ↑
                    하나씩 확인
```

반면 인덱스는 특정 컬럼의 값을 정렬된 구조로 관리하여 원하는 값이 있을 범위를 빠르게 좁힐 수 있도록 돕는다.

도서관에 책이 100만 권 있다고 생각해보자.

- 책이 아무 기준 없이 놓여 있다면 첫 번째 책부터 하나씩 확인해야 한다.
- 제목이 정렬된 색인이 있다면 전체 책을 확인하지 않고 원하는 책의 위치를 찾을 수 있다.

데이터베이스의 인덱스도 책 뒤편의 찾아보기와 비슷한 역할을 한다.

---

## 2. B-Tree 인덱스

PostgreSQL을 포함한 대부분의 관계형 데이터베이스는 기본적인 인덱스 구조로 B-Tree를 사용한다.

B-Tree는 인덱스 키를 정렬된 트리 구조로 관리한다. 검색할 때는 모든 값을 하나씩 확인하지 않고, 현재 값과 검색값을 비교하면서 필요한 방향으로 이동한다.

```text
전체 범위
    ↓
검색값이 포함된 범위 선택
    ↓
더 작은 하위 범위 선택
    ↓
원하는 키 발견
    ↓
실제 테이블 행의 위치 확인
```

B-Tree의 핵심은 검색 범위를 단계적으로 줄이는 것이다.

---

## 3. B-Tree의 기본 구조

B-Tree 인덱스는 검색을 시작하는 상위 노드에서 값의 범위를 비교하고, 원하는 값이 있을 하위 노드로 이동하는 구조이다.

예를 들어 `customer_id = 300`인 값을 찾는 과정을 단순화하면 다음과 같다.

```text
                 [ 200 | 500 ]
                 /      |      \
                /       |       \
         200보다 작음  200~500  500보다 큼
                         ↓
                    [ 300 | 400 ]
                         ↓
                     300 발견
                         ↓
                실제 데이터 위치 확인
```

구성 요소의 역할은 다음과 같이 이해할 수 있다.

| 구성 요소 | 역할 |
|---|---|
| Root Node | 탐색을 시작하며 검색값이 어느 범위에 있는지 판단한다. |
| 하위 노드 | 상위 노드에서 선택된 범위를 더 작은 범위로 나눈다. |
| Leaf Page | 인덱스 키와 실제 테이블 행을 찾기 위한 위치 정보를 가진다. |

실제 B-Tree는 많은 키와 여러 단계로 구성될 수 있지만, 탐색 원리는 정렬된 값을 기준으로 불필요한 범위를 제외하는 것이다.

---

## 4. B-Tree 탐색 과정

`orders` 테이블의 `customer_id`에 인덱스를 만들고 특정 고객의 주문을 조회한다고 가정한다.

```sql
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);
```

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 300;
```

실행계획은 다음과 같은 형태로 나타날 수 있다.

```text
Bitmap Heap Scan on orders
  (cost=4.47..27.82 rows=6 width=32)
  Recheck Cond: (customer_id = 300)
  ->  Bitmap Index Scan on idx_orders_customer_id
        (cost=0.00..4.47 rows=6 width=0)
        Index Cond: (customer_id = 300)
```

PostgreSQL은 모든 주문 행을 처음부터 확인하는 대신 `customer_id` 값이 정렬된 B-Tree 인덱스를 따라 탐색할 수 있다.

### 1단계: 검색 범위 선택

검색값 `300`을 상위 노드의 기준값과 비교한다. `300`은 `200`보다 크고 `500`보다 작으므로 `200~500` 범위로 이동한다.

### 2단계: 범위를 다시 축소

선택한 하위 범위에서 같은 방식으로 값을 비교한다. `300`을 발견하면 다른 범위는 더 이상 확인할 필요가 없다.

### 3단계: 실제 테이블 행 조회

인덱스에서 `300`을 찾으면 인덱스가 가진 위치 정보를 이용하여 필요한 테이블 행에 접근한다.

```text
Root에서 범위 판단
    ↓
해당 하위 노드로 이동
    ↓
Leaf Page에서 키 발견
    ↓
실제 테이블 행 조회
```

데이터가 많아질수록 모든 행을 순서대로 확인하는 방식과 비교해 검색 범위를 줄이는 구조의 장점이 커질 수 있다.

---

## 5. B-Tree가 활용되는 조건

B-Tree는 값이 정렬되어 있으므로 특정 값의 일치 여부뿐 아니라 크기 비교와 범위 검색에도 폭넓게 활용될 수 있다.

| 조건 유형 | SQL 예시 |
|---|---|
| 일치 검색 | `customer_id = 300` |
| 작은 값 검색 | `customer_id < 300` |
| 큰 값 검색 | `customer_id > 300` |
| 범위 검색 | `customer_id BETWEEN 200 AND 400` |

다만 인덱스가 존재한다고 해서 모든 쿼리가 반드시 그 인덱스를 사용하는 것은 아니다. 옵티마이저는 데이터의 양과 조회 범위 등을 고려하여 `Seq Scan`, `Index Scan`, `Bitmap Index Scan` 등의 실행 방법 중 적절한 계획을 선택한다.

## 6. 인덱스 생성

PostgreSQL에서는 `CREATE INDEX` 문으로 인덱스를 생성할 수 있다.

기본 문법:

```sql
CREATE INDEX 인덱스명
ON 테이블명 (컬럼명);
```

`orders` 테이블의 `customer_id`에 인덱스를 만드는 예시는 다음과 같다.

```sql
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);
```

상품 이름과 카테고리를 자주 검색한다면 다음과 같이 각각 인덱스를 만들 수 있다.

```sql
CREATE INDEX idx_products_name
ON products (product_name);

CREATE INDEX idx_products_category
ON products (category_id);
```

인덱스를 생성하면 해당 컬럼을 조회 조건으로 사용하는 일부 쿼리에서 더 유리한 실행계획이 선택될 수 있다.

---

## 7. 인덱스 삭제

필요하지 않은 인덱스는 `DROP INDEX` 문으로 삭제할 수 있다.

기본 문법:

```sql
DROP INDEX 인덱스명;
```

예시:

```sql
DROP INDEX idx_products_price;
```

`orders` 테이블에 생성된 인덱스의 목록과 정의는 `pg_indexes`에서 확인할 수 있다.

```sql
SELECT indexname,
       indexdef
FROM pg_indexes
WHERE tablename = 'orders';
```

인덱스를 생성하거나 삭제하기 전에는 실제 쿼리에서 사용되는지와 유지 비용을 함께 확인해야 한다.

---

## 8. 인덱스가 쓰기 성능에 미치는 영향

인덱스는 조회 성능에 도움을 줄 수 있지만 무료로 유지되는 구조는 아니다. 테이블의 데이터가 변경되면 관련 인덱스도 함께 갱신해야 한다.

새로운 상품을 추가하는 상황을 살펴보자.

```sql
INSERT INTO products (
    product_id,
    product_name,
    category_id
)
VALUES (
    1001,
    '무선 키보드',
    3
);
```

테이블에 여러 인덱스가 있다면 개념적으로 다음 작업이 함께 발생한다.

```text
products 테이블에 새 상품 저장
    ↓
idx_products_name 갱신
    ↓
idx_products_category 갱신
    ↓
그 밖의 관련 인덱스 갱신
```

인덱스가 많아질수록 `INSERT`, `UPDATE`, `DELETE` 시 유지해야 하는 인덱스도 많아질 수 있다.

- `INSERT`: 새로운 행의 인덱스 키를 추가해야 한다.
- `UPDATE`: 인덱스 대상 컬럼의 값이 바뀌면 관련 키를 변경해야 한다.
- `DELETE`: 삭제된 행에 해당하는 인덱스 정보도 정리해야 한다.

즉, 인덱스는 조회 성능을 얻는 대신 쓰기 작업과 저장 공간에 추가 비용을 발생시킨다.

## 9. 인덱스는 많을수록 좋은가?

인덱스가 많으면 다양한 조회 조건을 지원할 수 있지만, 모든 컬럼에 무작정 인덱스를 만드는 것은 적절하지 않다.

| 얻는 효과 | 발생하는 비용 |
|---|---|
| 특정 조건의 검색 범위를 줄일 수 있다. | 인덱스를 저장할 공간이 필요하다. |
| 일부 조회 쿼리의 성능을 향상시킬 수 있다. | 데이터 변경 시 관련 인덱스를 갱신해야 한다. |
| 옵티마이저가 선택할 수 있는 실행 방법이 늘어난다. | 불필요한 인덱스가 많으면 쓰기 작업의 부담이 커질 수 있다. |

인덱스를 설계할 때는 다음을 함께 고려해야 한다.

- 해당 컬럼이 조회 조건에 자주 사용되는가?
- 조회 성능 개선의 필요성이 큰가?
- 테이블의 데이터 변경이 얼마나 자주 발생하는가?
- 이미 비슷한 역할을 하는 인덱스가 존재하는가?
- 인덱스 생성 후 실행계획이 실제로 달라지는가?

```text
자주 사용하는 조회 조건
        +
데이터 변경 빈도
        +
저장 공간과 유지 비용
        ↓
인덱스 생성 여부 판단
```

## 10. 인덱스와 실행계획의 관계

인덱스를 생성했다는 사실만으로 쿼리 성능이 반드시 향상되었다고 판단할 수는 없다. 옵티마이저가 실제로 해당 인덱스를 사용하는지 실행계획으로 확인해야 한다.

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 300;
```

확인할 수 있는 대표적인 접근 방식은 다음과 같다.

| 실행계획 노드 | 의미 |
|---|---|
| `Seq Scan` | 테이블을 순차적으로 읽는다. |
| `Index Scan` | 인덱스로 위치를 찾은 뒤 테이블 행에 접근한다. |
| `Bitmap Index Scan` | 인덱스에서 조건에 맞는 위치를 비트맵 형태로 모은다. |
| `Bitmap Heap Scan` | 비트맵에 기록된 위치를 이용하여 테이블 행을 읽는다. |

따라서 인덱스를 만든 뒤에는 다음 흐름으로 확인하는 것이 중요하다.

```text
인덱스 생성
    ↓
조회 SQL에 EXPLAIN 적용
    ↓
선택된 스캔 방식 확인
    ↓
실제 조회 범위와 비용을 고려하여 효과 판단
```

## 11. 핵심 용어 정리

| 용어 | 의미 |
|---|---|
| Index | 특정 컬럼의 값을 이용해 원하는 데이터의 위치를 빠르게 찾도록 돕는 별도의 자료구조 |
| B-Tree | 키를 정렬된 트리 구조로 관리하며 검색 범위를 단계적으로 줄이는 인덱스 구조 |
| Root Node | B-Tree 탐색이 시작되는 최상위 노드 |
| Leaf Page | 인덱스 키와 실제 테이블 행을 찾기 위한 위치 정보가 저장되는 말단 영역 |
| `Seq Scan` | 테이블의 행을 순서대로 읽으며 조건에 맞는 데이터를 찾는 방식 |
| `CREATE INDEX` | 인덱스를 생성하는 SQL 명령 |
| `DROP INDEX` | 인덱스를 삭제하는 SQL 명령 |
| Index Maintenance | 데이터 변경에 맞추어 인덱스의 키와 구조를 갱신하는 작업 |

## 12. 오늘 배운 내용 정리

### B-Tree 구조와 탐색

- B-Tree 인덱스는 키를 정렬된 트리 구조로 관리한다.
- 검색값과 노드의 기준값을 비교하면서 필요한 방향으로 이동한다.
- 전체 데이터를 하나씩 확인하지 않고 검색 범위를 단계적으로 줄인다.
- 원하는 키를 찾으면 저장된 위치 정보를 이용해 실제 테이블 행에 접근한다.
- `=`, `<`, `>`, `BETWEEN`과 같은 비교 및 범위 검색에 폭넓게 활용할 수 있다.

### 인덱스 관리

- `CREATE INDEX`로 인덱스를 생성할 수 있다.
- `DROP INDEX`로 필요하지 않은 인덱스를 삭제할 수 있다.
- `pg_indexes`를 조회하여 테이블의 인덱스 목록과 정의를 확인할 수 있다.
- 인덱스를 만든 뒤에는 `EXPLAIN`으로 실제 사용 여부를 확인해야 한다.

### 조회와 쓰기의 Trade-off

- 인덱스는 일부 조회 쿼리의 검색 범위를 줄여 성능을 높일 수 있다.
- 인덱스는 별도의 저장 공간을 사용한다.
- 데이터가 추가·수정·삭제되면 관련 인덱스도 함께 갱신되어야 한다.
- 인덱스가 많을수록 쓰기 작업의 유지 비용이 커질 수 있다.
- 자주 사용하는 조회 조건과 데이터 변경 빈도를 함께 고려하여 필요한 인덱스만 만들어야 한다.

## 한 문장 정리

> B-Tree 인덱스는 정렬된 트리에서 검색 범위를 단계적으로 줄여 조회를 빠르게 하지만, 데이터 변경 시 함께 갱신해야 하므로 조회 성능과 쓰기 비용을 함께 고려해 설계해야 한다.
