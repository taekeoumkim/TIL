# 2026-09-14 쿼리 재작성 전후 실행계획 비교와 개선 효과 분석

## 학습 목표

- 인덱스 추가 또는 쿼리 재작성 전후의 실행계획 변화를 비교할 수 있다.
- `EXPLAIN ANALYZE` 결과를 바탕으로 튜닝 전 기준 성능을 기록할 수 있다.
- 스캔 방식, 예상 비용, 실제 실행 시간의 변화를 통해 개선 효과를 판단할 수 있다.
- 튜닝 결과와 한계를 객관적인 수치로 정리할 수 있다.

## 1. 튜닝은 개선 전 상태 기록부터 시작한다

실행계획에서 병목을 발견했다고 해서 바로 인덱스를 추가하거나 쿼리를 변경하면 개선 효과를 정확히 증명하기 어렵다. 튜닝 전 실행 방식과 성능을 먼저 기록해야 변경 후 결과와 비교할 기준이 생긴다.

```text
현재 실행계획 측정
    ↓
병목 또는 개선 대상 확인
    ↓
개선 가설 설정
    ↓
인덱스 추가 또는 쿼리 변경
    ↓
동일한 쿼리 재측정
    ↓
전후 결과 비교 및 결론 작성
```

튜닝 전에는 `EXPLAIN ANALYZE`를 사용하여 다음 항목을 기록한다.

| 기록 항목 | 확인 목적 |
|---|---|
| 실행계획의 주요 노드 | 데이터가 어떤 방식으로 처리되는지 확인 |
| 스캔 방식 | `Seq Scan`, `Parallel Seq Scan`, `Index Scan` 등의 사용 여부 확인 |
| 총 `cost` | 옵티마이저가 예상한 상대적 비용 기록 |
| 예상 `rows` | 옵티마이저가 예측한 결과 행 수 확인 |
| 실제 `rows` | 실제로 처리하거나 반환한 행 수 확인 |
| `actual time` | 각 노드의 실제 실행 시간 확인 |
| `Execution Time` | 전체 쿼리의 실제 실행 시간 기록 |

## 2. 쿼리 재작성 전 실행계획과 성능 기록

Bike Store의 `order_items` 테이블에서 특정 상품이 포함된 주문 항목을 조회한다고 가정한다.

```sql
EXPLAIN ANALYZE
SELECT
    order_id,
    product_id,
    quantity,
    list_price
FROM order_items
WHERE product_id = 50;
```

튜닝 전 실행계획은 다음과 같은 형태로 나타났다.

```text
Gather
  (actual time=0.555..256.860 rows=4689 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  └─ Parallel Seq Scan on order_items
       (actual time=0.017..34.207 rows=1563 loops=3)
       Filter: (product_id = 50)
       Rows Removed by Filter: 511741

Planning Time: 0.162 ms
Execution Time: 257.162 ms
```

### 실행계획 해석

`Parallel Seq Scan`은 여러 작업자가 테이블의 데이터를 나누어 순차적으로 읽는 방식이다. 이 결과에서는 인덱스로 대상 행을 바로 찾지 않고, `order_items` 테이블을 순차적으로 읽으면서 `product_id = 50`인 행을 찾고 있다.

```text
order_items 데이터 병렬 순차 조회
    ↓
product_id = 50 조건 검사
    ↓
조건에 맞는 행 반환
```

튜닝 전 기준 성능은 다음과 같이 정리할 수 있다.

| 항목 | 측정 결과 |
|---|---|
| 조회 조건 | `product_id = 50` |
| 스캔 방식 | `Parallel Seq Scan` |
| 실제 조회 행 수 | 4,689개 |
| 전체 실행 시간 | 약 257ms |

이 값은 인덱스 추가나 쿼리 변경 후 성능이 실제로 개선되었는지 판단하는 기준선이 된다.

### 기준 성능 기록이 필요한 이유

- 변경 전후에 어떤 실행 방식이 선택되었는지 비교할 수 있다.
- 실행 시간이 얼마나 감소하거나 증가했는지 계산할 수 있다.
- 예상과 달리 개선되지 않은 경우에도 그 사실을 확인할 수 있다.
- 단순한 느낌이 아니라 실행계획과 측정값을 근거로 튜닝 결과를 설명할 수 있다.

## 3. 개선 가설을 세우고 한 가지 요소를 변경한다

튜닝은 실행계획에서 확인한 문제를 바탕으로 가설을 세운 뒤 검증하는 과정이다.

예를 들어 특정 고객의 주문을 검색할 때 `orders` 테이블에서 `Seq Scan`이 발생한다면 다음과 같은 가설을 세울 수 있다.

> `customer_id`로 일부 주문만 자주 조회한다면, 해당 열에 인덱스를 생성했을 때 필요한 행을 더 빠르게 찾을 수 있을 것이다.

가설을 검증하기 위해 `customer_id`에 인덱스를 생성한다.

```sql
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);
```

한 번에 여러 요소를 함께 바꾸면 어떤 변경이 성능 개선의 원인이었는지 구분하기 어렵다. 따라서 가능한 한 하나의 요소만 변경하고 다시 측정한다.

```text
문제 확인: Seq Scan 발생
    ↓
가설 설정: customer_id 인덱스가 조회 범위를 줄일 것이다
    ↓
변경 적용: 인덱스 생성
    ↓
재측정: 동일한 조회 쿼리에 EXPLAIN ANALYZE 실행
```

## 4. 변경 후 동일한 쿼리를 재측정한다

인덱스를 생성한 후에는 다른 조건을 바꾸지 않고 같은 쿼리를 다시 실행한다.

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 100;
```

인덱스가 선택되면 다음과 같은 실행계획을 확인할 수 있다.

```text
Index Scan using idx_orders_customer_id on orders
  Index Cond: (customer_id = 100)

Planning Time: ...
Execution Time: ...
```

개선 전후의 데이터 접근 방식은 다음과 같이 달라질 수 있다.

| 구분 | 스캔 방식 | 데이터 접근 방법 |
|---|---|---|
| 개선 전 | `Seq Scan` | 테이블을 순차적으로 읽으며 조건 검사 |
| 개선 후 | `Index Scan` | `customer_id` 인덱스에서 조건에 맞는 행을 탐색 |

중요한 것은 인덱스를 생성했다는 사실 자체가 아니라 다음 두 가지를 확인하는 것이다.

1. 실행계획에서 실제로 `Index Scan`이 선택되었는가?
2. 실제 `Execution Time`이 개선 전보다 감소했는가?

데이터의 양, 값의 분포, 조회 조건으로 반환되는 행의 비율에 따라 옵티마이저가 인덱스보다 `Seq Scan`이 효율적이라고 판단할 수도 있다. 따라서 인덱스 생성만으로 성능 개선을 단정하면 안 된다.

## 5. 개선 전후 실행계획 비교하기

`product_id` 조건으로 주문 상품을 조회하는 쿼리에 인덱스를 적용했다고 가정한다.

### 개선 전

```text
Seq Scan on order_items
  (cost=... rows=... width=...)

Execution Time: ...
```

### 개선 후

```text
Index Scan using idx_order_items_product_id on order_items
  (cost=... rows=... width=...)

Execution Time: ...
```

단순히 “인덱스를 추가해서 빨라졌다”라고 표현하는 대신 동일한 지표를 표로 비교한다.

| 비교 항목 | 개선 전 | 개선 후 | 해석 |
|---|---|---|---|
| 조회 조건 | `product_id = 50` | `product_id = 50` | 같은 조건인지 확인 |
| 스캔 방식 | `Seq Scan` 또는 `Parallel Seq Scan` | `Index Scan` | 데이터 접근 방식의 변화 확인 |
| 총 `cost` | 개선 전 비용 | 개선 후 비용 | 옵티마이저 예상 비용 비교 |
| 예상 `rows` | 개선 전 예상 행 수 | 개선 후 예상 행 수 | 예측값 변화 확인 |
| 실제 `rows` | 개선 전 실제 행 수 | 개선 후 실제 행 수 | 같은 결과를 반환하는지 확인 |
| `Execution Time` | 개선 전 실행 시간 | 개선 후 실행 시간 | 실제 성능 개선 여부 확인 |

### 실행 시간 감소율 계산

개선 효과는 실행 시간의 감소율로 표현할 수 있다.

$$
\text{실행 시간 감소율}(\%)
=
\frac{\text{개선 전 실행 시간}-\text{개선 후 실행 시간}}
{\text{개선 전 실행 시간}}
\times 100
$$

예를 들어 실행 시간이 10ms에서 2ms로 감소했다면 다음과 같다.

$$
\frac{10-2}{10}\times100=80\%
$$

따라서 실행 시간이 약 80% 감소했다고 정리할 수 있다.

## 6. 튜닝 결과 보고서 작성 방법

튜닝 보고서는 변경 내용만 나열하지 않고 문제, 가설, 변경, 측정 결과, 결론을 연결해 작성한다.

### 보고서 구성

| 항목 | 작성 내용 |
|---|---|
| 대상 쿼리 | 어떤 데이터를 어떤 조건으로 조회하는지 |
| 개선 전 문제 | 스캔 방식, 처리 행 수, 실행 시간 등 |
| 개선 가설 | 어떤 변경이 왜 도움이 될 것으로 예상했는지 |
| 적용한 변경 | 생성한 인덱스 또는 변경한 쿼리 구조 |
| 개선 후 결과 | 변경된 실행계획과 실제 측정값 |
| 개선 효과 | 실행 시간 차이와 감소율 |
| 한계 및 판단 | 개선 여부와 추가 확인이 필요한 사항 |

### 보고 문장 예시

> `product_id` 인덱스 적용 후 스캔 방식이 `Seq Scan`에서 `Index Scan`으로 변경되었다. 동일한 조건에서 `EXPLAIN ANALYZE`를 다시 실행한 결과 실제 실행 시간도 감소하여, 해당 조회 쿼리에 대한 인덱스 적용 효과를 확인했다.

실행계획이 `Index Scan`으로 바뀌었더라도 실행 시간이 줄지 않았다면 성공적인 튜닝으로 단정할 수 없다. 반대로 실행 노드의 명칭만 보는 것이 아니라 실제 처리 행 수와 실행 시간을 함께 비교해야 한다.
