# 2026-09-09 SQL 실행 흐름과 옵티마이저

## 학습 목표

- SQL 쿼리가 파싱, 최적화, 실행 단계를 거쳐 처리되는 흐름을 설명할 수 있다.
- 각 단계에서 데이터베이스가 수행하는 작업을 구분할 수 있다.
- 하나의 SQL에도 여러 실행 방법이 존재할 수 있음을 이해한다.
- 옵티마이저와 실행계획의 역할을 설명할 수 있다.
- 인덱스가 존재하더라도 항상 사용되는 것은 아님을 이해한다.

---

## 1. SQL은 작성한 즉시 실행되지 않는다

사용자가 작성한 SQL은 데이터베이스가 곧바로 테이블에서 실행하는 명령이 아니다. 데이터베이스는 먼저 SQL을 해석하고, 데이터를 가져올 방법을 결정한 다음, 선택한 방법에 따라 실제 데이터를 읽는다.

SQL의 기본 실행 흐름은 다음과 같다.

```text
SQL 작성
    ↓
파싱(Parsing)
    ↓
최적화(Optimization)
    ↓
실행(Execution)
    ↓
결과 반환
```

예를 들어 온라인 쇼핑몰에서 주문 번호가 `1050`인 주문을 조회한다고 가정한다.

```sql
SELECT *
FROM orders
WHERE order_id = 1050;
```

사용자에게는 단순한 한 줄의 SQL이지만, 데이터베이스 내부에서는 파싱 → 최적화 → 실행의 과정을 차례로 거친다.

---

## 2. 1단계: 파싱(Parsing)

파싱은 데이터베이스가 입력받은 SQL의 문법과 의미가 올바른지 확인하는 단계이다.

주요 확인 내용은 다음과 같다.

- `SELECT`, `FROM`, `WHERE` 등의 SQL 문법이 올바른가?
- 조회하려는 테이블이 실제로 존재하는가?
- SQL에서 사용한 컬럼이 해당 테이블에 존재하는가?
- SQL을 내부에서 처리할 수 있는 구조로 변환할 수 있는가?

데이터베이스는 확인을 마친 SQL을 내부적으로 이해할 수 있는 파스 트리(Parse Tree) 형태로 만든다.

존재하지 않는 컬럼을 사용한 경우를 살펴보자.

```sql
SELECT *
FROM orders
WHERE wrong_column = 1050;
```

`orders` 테이블에 `wrong_column`이 없다면 파싱 과정에서 오류가 발견되며, 최적화와 실행 단계로 넘어가지 못한다.

```text
SQL Error [42703]: "wrong_column" 이름의 칼럼은 없습니다.
```

즉, 파싱은 SQL을 실제로 실행하기 전에 문법과 데이터베이스 객체의 유효성을 검사하는 과정이다.

---

## 3. 2단계: 최적화(Optimization)

파싱을 통과한 SQL에는 같은 결과를 만드는 여러 실행 방법이 존재할 수 있다. 최적화 단계에서는 가능한 방법들을 검토하고, 그중 비용이 가장 낮을 것으로 예상되는 실행 방법을 선택한다.

다음 SQL을 실행하는 방법을 생각해보자.

```sql
SELECT *
FROM orders
WHERE order_id = 1050;
```

데이터베이스가 검토할 수 있는 대표적인 방법은 다음과 같다.

| 실행 방법 | 설명 |
|---|---|
| 테이블을 순서대로 확인 | `orders` 테이블의 데이터를 차례로 읽으며 조건에 맞는 행을 찾는다. |
| 인덱스를 이용하여 탐색 | `order_id`에 사용할 수 있는 인덱스를 통해 대상 행의 위치를 찾는다. |

어떤 방법을 사용할지는 SQL 문장에 직접 적혀 있지 않다. 여러 후보를 비교하여 실행 방법을 결정하는 주체가 옵티마이저이다.

최적화가 적절하지 않으면 결과는 같더라도 불필요하게 많은 데이터를 읽거나 자원을 사용하여 쿼리 성능이 저하될 수 있다.

---

## 4. 3단계: 실행(Execution)

실행 단계에서는 최적화 과정에서 선택된 실행계획에 따라 실제 데이터에 접근하고 결과를 반환한다.

이 단계에서 이루어지는 작업은 다음과 같다.

- 테이블 또는 인덱스에 접근한다.
- 조건에 맞는 데이터를 찾는다.
- 필요한 연산을 수행한다.
- 최종 결과를 사용자에게 반환한다.

실행계획이 비효율적이면 데이터 접근량과 CPU·메모리 사용량이 증가하여 응답이 느려질 수 있다.

---

## 5. SQL 실행 단계 비교

| 단계 | 하는 일 | 문제가 발생했을 때의 결과 |
|---|---|---|
| 파싱(Parsing) | SQL 문법, 테이블·컬럼 존재 여부를 확인하고 파스 트리를 생성한다. | 문법 오류 또는 존재하지 않는 객체 참조 오류가 발생한다. |
| 최적화(Optimization) | 여러 실행 경로를 비교하여 비용이 가장 낮을 것으로 예상되는 실행계획을 선택한다. | 비효율적인 실행계획이 선택되어 성능이 저하될 수 있다. |
| 실행(Execution) | 실행계획에 따라 실제 데이터에 접근하고 결과를 반환한다. | 응답이 느려지거나 많은 시스템 자원을 사용할 수 있다. |

세 단계의 차이를 간단히 정리하면 다음과 같다.

```text
파싱: 이 SQL이 올바른가?
최적화: 어떤 방법으로 실행할 것인가?
실행: 선택한 방법으로 실제 데이터를 가져온다.
```

---

## 6. 옵티마이저(Optimizer)

옵티마이저는 하나의 SQL을 실행할 수 있는 여러 방법을 비교하고, 그중 효율적이라고 판단되는 방법을 선택하는 데이터베이스의 구성 요소이다.

예를 들어 고객 번호가 `500`인 고객 한 명을 조회한다고 가정한다.

```sql
SELECT *
FROM customers
WHERE customer_id = 500;
```

이 SQL의 결과는 하나이지만, 결과를 찾는 방법은 하나가 아니다.

### 방법 1: 테이블을 순서대로 확인

테이블의 데이터를 차례로 읽으면서 `customer_id`가 `500`인 행을 찾는다.

```text
customer_id 1 확인
    ↓
customer_id 2 확인
    ↓
customer_id 3 확인
    ↓
...
    ↓
customer_id 500 확인
```

### 방법 2: 인덱스를 이용하여 탐색

`customer_id`에 사용할 수 있는 인덱스가 있다면, 인덱스에서 `500`의 위치를 찾은 뒤 필요한 고객 데이터에 접근할 수 있다.

```text
customer_id 인덱스 확인
    ↓
500의 위치 탐색
    ↓
필요한 고객 데이터 조회
```

사용자는 SQL에 원하는 결과만 작성했을 뿐, 테이블을 처음부터 읽을지 인덱스를 사용할지는 지정하지 않았다. 이 선택을 담당하는 것이 옵티마이저이다.

---

## 7. 실행계획(Execution Plan)

실행계획은 옵티마이저가 최종적으로 선택한 구체적인 SQL 실행 방법이다.

```text
SQL
    ↓
옵티마이저
    ├─ 테이블을 순서대로 읽을까?
    └─ 인덱스를 사용할까?
    ↓
실행계획 선택
    ↓
실제 실행
```

SQL은 **무엇을 조회할지** 표현하고, 실행계획은 데이터베이스가 그 결과를 **어떻게 가져올지** 나타낸다.

| 구분 | 의미 |
|---|---|
| SQL | 사용자가 원하는 결과를 표현한 명령문 |
| 옵티마이저 | 가능한 실행 방법을 비교하고 하나를 선택하는 구성 요소 |
| 실행계획 | 옵티마이저가 선택한 구체적인 데이터 접근 및 처리 방법 |

---

## 8. 인덱스가 있어도 반드시 사용하지는 않는다

조건에 사용할 수 있는 인덱스가 존재하더라도 옵티마이저가 항상 인덱스를 선택하는 것은 아니다.

옵티마이저는 테이블을 순서대로 읽는 방법과 인덱스를 이용하는 방법 등 여러 후보를 비교한 뒤, 더 효율적이라고 예상되는 실행계획을 선택한다. 따라서 인덱스의 존재와 실제 인덱스 사용은 구분해야 한다.

```text
인덱스가 존재한다
≠
해당 쿼리가 반드시 인덱스를 사용한다
```

SQL의 결과가 같더라도 선택된 실행계획에 따라 처리 방식과 속도가 달라질 수 있다.

---

## 9. 같은 SQL의 실행 속도가 달라질 수 있는 이유

같은 SQL을 실행하더라도 데이터의 양이나 상태 등이 달라지면 옵티마이저가 이전과 다른 실행계획을 선택할 수 있다.

```text
SQL 문장은 동일함
    ↓
최적화 단계의 판단이 달라짐
    ↓
다른 실행계획 선택
    ↓
실행 방식과 속도가 달라질 수 있음
```

따라서 쿼리가 느릴 때는 SQL 문장만 보는 것이 아니라, 옵티마이저가 어떤 실행계획을 선택했는지도 확인해야 한다.

---

## 10. 핵심 용어 정리

| 용어 | 의미 |
|---|---|
| Parsing | SQL 문법과 테이블·컬럼의 유효성을 확인하고 내부 구조로 변환하는 단계 |
| Optimization | 여러 실행 방법을 비교하여 효율적이라고 예상되는 실행계획을 선택하는 단계 |
| Execution | 선택된 실행계획에 따라 실제 데이터에 접근하고 결과를 반환하는 단계 |
| Optimizer | 가능한 실행 방법을 비교하고 적절한 방법을 선택하는 데이터베이스 구성 요소 |
| Execution Plan | 옵티마이저가 선택한 구체적인 SQL 실행 방법 |
| Table Scan | 테이블의 데이터를 순서대로 확인하며 필요한 행을 찾는 방식 |
| Index | 특정 값을 더 효율적으로 찾을 수 있도록 데이터의 위치를 관리하는 구조 |
| Parse Tree | 데이터베이스가 SQL의 구조를 이해하고 처리하기 위해 만든 내부 표현 |

## 11. 오늘 배운 내용 정리

### SQL 실행 흐름

- SQL은 작성 즉시 실행되는 것이 아니라 파싱 → 최적화 → 실행 단계를 거친다.
- 파싱 단계에서는 SQL 문법과 테이블·컬럼의 존재 여부를 확인한다.
- 최적화 단계에서는 여러 실행 방법 중 비용이 가장 낮을 것으로 예상되는 방법을 선택한다.
- 실행 단계에서는 선택된 실행계획에 따라 실제 데이터를 읽고 결과를 반환한다.

### 옵티마이저와 실행계획

- 하나의 SQL에도 테이블을 순서대로 읽거나 인덱스를 이용하는 등 여러 실행 방법이 존재할 수 있다.
- 옵티마이저는 가능한 실행 방법들을 비교하여 적절한 방법을 선택한다.
- 옵티마이저가 선택한 구체적인 실행 방법을 실행계획이라고 한다.
- 인덱스가 존재하더라도 옵티마이저가 반드시 인덱스를 선택하는 것은 아니다.

### 성능 관점

- 같은 결과를 반환하는 SQL이라도 실행계획에 따라 속도와 자원 사용량이 달라질 수 있다.
- 데이터 상태 등이 변하면 같은 SQL에서도 다른 실행계획이 선택될 수 있다.
- 느린 쿼리의 원인을 파악하려면 SQL뿐 아니라 실제 실행계획도 함께 살펴봐야 한다.

## 한 문장 정리

> 데이터베이스는 SQL을 파싱한 뒤 옵티마이저로 실행계획을 선택하고, 그 계획에 따라 데이터를 실제로 조회한다.
