# 2026-09-09 인덱스가 효과적인 경우와 비효과적인 경우

## 학습 목표

- 인덱스가 쿼리 성능에 영향을 미치는 조건을 설명할 수 있다.
- 카디널리티와 선택도의 의미를 구분할 수 있다.
- 인덱스가 효과적인 경우와 비효과적인 경우를 판단할 수 있다.
- `WHERE`절의 작성 방식이 인덱스 활용에 미치는 영향을 이해할 수 있다.
- 복합 인덱스에서 컬럼 순서가 중요한 이유를 이해할 수 있다.
- 테이블과 쿼리의 특성을 바탕으로 인덱스 추가 여부를 판단할 수 있다.

---

## 1. 인덱스는 항상 쿼리를 빠르게 만들지 않는다

인덱스는 B-Tree와 같은 구조를 이용해 검색 범위를 줄일 수 있도록 돕는다. 하지만 인덱스를 만들었다고 해서 모든 쿼리가 빨라지는 것은 아니다.

인덱스의 효과는 다음과 같은 조건에 따라 달라진다.

- 컬럼에 서로 다른 값이 얼마나 많은가?
- 조건을 적용한 뒤 전체 데이터 중 몇 행이 남는가?
- 테이블의 규모가 얼마나 큰가?
- 조회와 데이터 변경 중 어떤 작업이 더 자주 발생하는가?
- `WHERE`절이 인덱스를 활용하기 좋은 형태로 작성되었는가?
- 복합 인덱스라면 조건과 인덱스 컬럼 순서가 잘 맞는가?

인덱스는 무조건 빠르게 해주는 장치가 아니라, 테이블과 쿼리의 조건에 따라 효과가 달라지는 도구이다.

---

## 2. 카디널리티(Cardinality)

카디널리티는 컬럼에 서로 다른 값이 얼마나 많이 존재하는지를 나타낸다.

| 컬럼 예시 | 값의 특성 | 카디널리티 |
|---|---|---|
| `user_id` | 사용자마다 고유한 값 | 매우 높음 |
| `email` | 사용자마다 대부분 다른 값 | 높음 |
| `country` | 약 20개의 국가 값 | 낮은 편 |
| `status` | 가입·탈퇴 등 3~4종 | 낮음 |
| `gender` | 남·여 등 소수의 값 | 매우 낮음 |

고유한 값이 많을수록 카디널리티가 높고, 반복되는 값의 종류가 적을수록 카디널리티가 낮다.

```text
서로 다른 값이 많음 → 카디널리티가 높음
서로 다른 값이 적음 → 카디널리티가 낮음
```

일반적으로 카디널리티가 높은 컬럼은 특정 값을 조회할 때 소수의 행만 찾을 가능성이 크므로 인덱스 효과를 기대하기 좋다.

---

## 3. 선택도(Selectivity)

선택도는 특정 조건을 적용했을 때 조건을 만족하는 행이 전체 행에서 차지하는 비율이다.

$$
\text{선택도} = \frac{\text{조건을 만족하는 행 수}}{\text{전체 행 수}} \times 100
$$

- 선택도가 낮다: 조건을 적용한 뒤 남는 행이 적다.
- 선택도가 높다: 조건을 적용한 뒤 남는 행이 많다.

인덱스는 일반적으로 선택도가 낮은 조건에서 효과가 크다. 인덱스를 통해 전체 데이터 중 필요한 소수의 행만 찾아갈 수 있기 때문이다.

---

## 4. 카디널리티와 선택도의 관계

온라인 예매 서비스의 `orders` 테이블에 100만 건의 주문이 있다고 가정한다.

### 특정 고객의 주문 조회

```sql
SELECT *
FROM orders
WHERE customer_id = 12345;
```

100만 건 중 특정 고객의 주문이 3건이라면 다음과 같다.

```text
전체 행              1,000,000건
조건을 만족하는 행           3건
선택도                    0.0003%
```

`customer_id`는 고객마다 거의 다른 값을 가지므로 카디널리티가 높다. 또한 특정 고객을 검색했을 때 전체 중 3건만 남으므로 선택도는 매우 낮다.

이 경우 인덱스로 필요한 몇 건만 찾아가는 방식이 효율적일 수 있다.

### 결제 완료 주문 전체 조회

```sql
SELECT *
FROM orders
WHERE payment_status = '결제완료';
```

결제 완료 상태가 전체 주문의 80%라면 다음과 같다.

```text
전체 행              1,000,000건
조건을 만족하는 행     800,000건
선택도                       80%
```

`payment_status`는 결제완료·취소·결제대기처럼 값의 종류가 적으므로 카디널리티가 낮다. 또한 조건을 적용해도 전체의 80%가 남으므로 선택도가 높다.

이 경우 인덱스로 80만 건의 위치를 찾고 테이블 행에 반복해서 접근하는 것보다 테이블을 순서대로 읽는 편이 더 효율적일 수 있다.

### 핵심 관계

| 카디널리티 | 선택도 | 일반적인 인덱스 효과 |
|---|---|---|
| 높음 | 낮음 | 효과를 기대하기 좋음 |
| 낮음 | 높음 | 효과가 작을 수 있음 |

중요한 것은 단순히 인덱스의 존재 여부가 아니라, 조건을 사용했을 때 실제로 얼마나 적은 데이터를 골라낼 수 있는가이다.

## 5. 인덱스가 효과적인 경우

다음과 같은 조건에서는 일반적으로 인덱스의 효과를 기대하기 좋다.

### 카디널리티가 높은 컬럼

사용자 ID, 이메일, 주문번호처럼 서로 다른 값이 많은 컬럼은 특정 값으로 조회했을 때 소수의 행만 남는 경우가 많다.

### 선택도가 낮은 조회 조건

전체 데이터 중 극히 일부만 조회하는 조건은 인덱스를 이용해 불필요한 데이터 접근을 줄일 수 있다.

### 규모가 큰 테이블

수백만 건의 데이터를 매번 전체 스캔하는 것은 부담이 될 수 있다. 큰 테이블에서 소수의 행을 자주 찾는다면 인덱스가 효과적일 가능성이 높다.

### 자주 실행되는 조회

특정 조건의 조회가 하루에 수천 번 반복된다면, 인덱스 유지 비용이 있더라도 누적되는 조회 성능 개선 효과가 더 클 수 있다.

```text
높은 카디널리티
        +
낮은 선택도
        +
큰 테이블
        +
빈번한 조회
        ↓
인덱스 추가를 우선 검토
```

## 6. 인덱스가 비효과적인 경우

인덱스를 생성해도 실행계획에서 사용되지 않거나, 사용되더라도 이득이 크지 않은 대표적인 상황이 있다.

### 선택도가 높은 조건

성별이나 상태값처럼 값의 종류가 적고, 조건을 적용해도 전체 행의 상당 부분이 남는 경우이다.

예를 들어 직원 300명 중 280명이 재직 중이라고 가정한다.

```sql
CREATE INDEX idx_employees_status
ON employees (status);
```

```sql
SELECT *
FROM employees
WHERE status = '재직';
```

인덱스를 이용하면 `'재직'`을 찾은 뒤 약 280개의 테이블 행에 접근해야 한다. 반면 `Seq Scan`은 300개의 행을 한 번 순서대로 읽으면 된다.

```text
인덱스 사용
→ 인덱스에서 '재직' 탐색
→ 약 280개의 테이블 행에 다시 접근

Seq Scan
→ 테이블의 300개 행을 한 번 순서대로 읽음
```

옵티마이저는 두 방법의 비용을 비교하여 다음과 같이 `Seq Scan`을 선택할 수 있다.

```text
Seq Scan on employees
  Filter: (status = '재직')
```

### 규모가 작은 테이블

수백 건 이하의 작은 테이블은 전체를 읽는 비용 자체가 작을 수 있다. 이때는 인덱스를 탐색한 뒤 테이블에 접근하는 과정이 오히려 추가 부담이 될 수 있다.

### 쓰기 작업이 매우 빈번한 테이블

`INSERT`, `UPDATE`, `DELETE`가 자주 발생하면 관련 인덱스도 계속 갱신해야 한다. 조회 성능 개선보다 인덱스 유지 비용이 더 클 수 있다.

### 비효과적인 경우 요약

| 상황 | 인덱스 효과가 작을 수 있는 이유 |
|---|---|
| 낮은 카디널리티 | 같은 값을 가진 행이 많아 특정 값을 검색해도 많은 행이 남는다. |
| 높은 선택도 | 조건을 적용해도 전체 데이터의 상당 부분을 읽어야 한다. |
| 작은 테이블 | Full Table Scan 자체의 비용이 매우 작을 수 있다. |
| 쓰기 중심 테이블 | 데이터 변경 때마다 발생하는 인덱스 갱신 비용이 커진다. |

`Seq Scan`이 나타났다는 이유만으로 인덱스가 잘못되었다고 판단할 수는 없다. 옵티마이저가 테이블 크기와 통계정보 등을 바탕으로 전체를 읽는 편이 더 저렴하다고 판단한 결과일 수 있다.

## 7. 인덱스 존재와 실제 사용은 다르다

인덱스가 생성되어 있어도 옵티마이저는 비용을 비교한 뒤 인덱스를 사용하지 않을 수 있다.

```text
인덱스가 존재함
        ≠
실행계획에서 인덱스를 반드시 사용함
```

인덱스 사용 여부는 다음 요소에 영향을 받을 수 있다.

- 테이블의 크기
- 조건을 만족하는 예상 행 수
- 컬럼의 값 분포
- 통계정보
- 인덱스 접근 후 테이블 행을 읽는 비용

따라서 인덱스를 생성했다는 사실만 확인해서는 안 되며, `EXPLAIN`으로 실제 실행계획을 확인해야 한다.

```sql
EXPLAIN
SELECT *
FROM employees
WHERE status = '재직';
```

## 8. WHERE절에서 인덱스 컬럼을 가공하지 않기

일반적인 B-Tree 인덱스는 인덱스를 생성한 컬럼의 원래 값을 기준으로 정렬되어 있다.

```sql
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);
```

다음 쿼리는 인덱스 컬럼을 그대로 비교한다.

```sql
SELECT *
FROM orders
WHERE customer_id = 5000;
```

이 형태에서는 B-Tree에 정렬된 `customer_id` 값을 이용해 필요한 위치를 탐색하기 좋다.

반면 컬럼에 연산을 적용하면 기존 인덱스를 직접적인 탐색 조건으로 활용하기 어려울 수 있다.

```sql
SELECT *
FROM orders
WHERE customer_id + 1 = 5001;
```

사람이 보기에는 결국 `customer_id = 5000`을 찾는 조건이지만, 쿼리는 인덱스에 정렬된 원래 값이 아니라 `customer_id + 1`이라는 가공된 값을 기준으로 검사한다.

```text
일반 인덱스의 정렬 기준
1000  2000  3000  4000  5000  6000  ...

쿼리의 비교 기준
customer_id + 1
```

가능하면 인덱스 컬럼을 가공하지 않고 직접 비교하도록 조건을 작성하는 것이 좋다.

```sql
-- 권장
SELECT *
FROM orders
WHERE customer_id = 5000;
```

## 9. 함수와 연산이 인덱스 활용에 미치는 영향

인덱스 컬럼에 함수나 연산을 적용하면 일반 인덱스를 효율적으로 활용하지 못할 수 있다.

| 조건 형태 | 예시 | 일반 인덱스 활용 관점 |
|---|---|---|
| 컬럼을 그대로 비교 | `customer_id = 12345` | 활용하기 좋음 |
| 컬럼에 연산 적용 | `customer_id + 0 = 12345` | 활용하기 어려울 수 있음 |

핵심 원칙은 `WHERE`절에서 사용하는 컬럼과 인덱스의 기준값이 자연스럽게 일치하도록 조건을 작성하는 것이다.

```text
인덱스의 원래 컬럼 값
        ↓ 직접 비교
검색 범위를 효율적으로 축소
```

## 10. 복합 인덱스와 컬럼 순서

복합 인덱스는 여러 컬럼으로 구성된 인덱스이다. 복합 인덱스에서는 컬럼의 순서가 중요하다.

일반적으로 인덱스 앞쪽 컬럼에 조건이 있을수록 탐색 범위를 효과적으로 줄이기 좋다.

```text
복합 인덱스: (첫 번째 컬럼, 두 번째 컬럼, ...)

앞쪽 컬럼부터 정렬 구조가 형성됨
        ↓
앞쪽 컬럼에 맞는 조건이 있을 때
탐색 범위를 줄이기 좋음
```

따라서 복합 인덱스를 설계할 때는 단순히 조건에 등장하는 컬럼을 모두 넣는 것이 아니라, 실제 조회 조건과 컬럼 순서의 관계도 고려해야 한다.

## 11. 인덱스 추가 판단 사례

`orders` 테이블에 주문 데이터가 500만 건 있고, 고객센터에서 다음 조회를 하루에도 수천 번 실행한다고 가정한다.

```sql
SELECT *
FROM orders
WHERE order_number = 'ORD-20260816-583921';
```

`order_number`는 주문마다 거의 고유한 값이다. 이 컬럼의 인덱스 추가 여부를 네 가지 기준으로 판단할 수 있다.

### 1. 카디널리티가 충분히 높은가?

주문마다 서로 다른 주문번호를 사용하므로 카디널리티가 높다.

### 2. 조건을 적용했을 때 남는 행이 적은가?

특정 주문번호를 검색하면 보통 주문 한 건만 조회되므로 선택도가 매우 낮다.

### 3. 테이블의 규모가 충분히 큰가?

500만 건을 조회할 때마다 전체 스캔하는 것은 부담이 될 수 있다.

### 4. 쓰기 비용을 감당할 수 있는가?

새 주문이 추가될 때마다 인덱스도 갱신해야 한다. 그러나 특정 주문 조회가 매우 빈번하다면 조회 성능 개선 효과가 더 중요할 수 있다.

이 사례에서는 인덱스 추가를 우선 검토할 수 있다.

```sql
CREATE INDEX idx_orders_order_number
ON orders (order_number);
```

인덱스 추가 후에는 `EXPLAIN` 또는 `EXPLAIN ANALYZE`를 이용해 실제 실행계획과 성능 변화를 확인해야 한다.

## 12. 인덱스 추가 판단 체크리스트

| 확인 항목 | 효과를 기대하기 좋은 조건 | 신중하게 판단할 조건 |
|---|---|---|
| 카디널리티 | 서로 다른 값이 많음 | 값의 종류가 매우 적음 |
| 선택도 | 조건을 적용하면 소수의 행만 남음 | 조건을 적용해도 대부분의 행이 남음 |
| 테이블 규모 | 전체 스캔이 부담스러운 대규모 테이블 | 전체 스캔 비용이 작은 소규모 테이블 |
| 조회 빈도 | 동일한 조회가 자주 반복됨 | 조회가 거의 발생하지 않음 |
| 쓰기 빈도 | 쓰기 비용보다 조회 개선 효과가 큼 | `INSERT`·`UPDATE`·`DELETE`가 매우 빈번함 |
| 조건 작성 | 인덱스 컬럼을 그대로 비교함 | 인덱스 컬럼에 함수나 연산을 적용함 |
| 실행계획 | 인덱스 사용으로 처리 범위·비용이 감소함 | 인덱스를 만들어도 `Seq Scan`이 더 저렴함 |

실무적인 판단 흐름은 다음과 같다.

```text
자주 실행되는 쿼리인가?
        ↓
조건 컬럼의 카디널리티가 높은가?
        ↓
조건의 선택도가 낮은가?
        ↓
테이블 규모가 충분히 큰가?
        ↓
쓰기·저장 비용을 감당할 수 있는가?
        ↓
EXPLAIN으로 실제 실행계획 확인
```

## 13. 핵심 용어 정리

| 용어 | 의미 |
|---|---|
| Cardinality | 컬럼에 존재하는 서로 다른 값의 수 또는 다양성 |
| Selectivity | 조건을 만족하는 행이 전체 행에서 차지하는 비율 |
| Low Selectivity | 조건을 적용한 뒤 남는 행의 비율이 작은 상태 |
| High Selectivity | 조건을 적용한 뒤 남는 행의 비율이 큰 상태 |
| Full Table Scan | 테이블의 전체 데이터를 순서대로 읽는 방식 |
| Write-heavy Table | `INSERT`, `UPDATE`, `DELETE` 같은 쓰기 작업이 매우 빈번한 테이블 |
| Composite Index | 두 개 이상의 컬럼으로 구성된 인덱스 |
| Index Maintenance | 데이터 변경에 맞추어 인덱스 정보를 갱신하는 작업 |

## 14. 오늘 배운 내용 정리

### 카디널리티와 선택도

- 카디널리티는 컬럼에 서로 다른 값이 얼마나 많이 존재하는지를 의미한다.
- 선택도는 조건을 만족하는 행이 전체에서 차지하는 비율이다.
- 일반적으로 카디널리티가 높고 선택도가 낮을수록 인덱스 효과가 크다.
- 인덱스가 있는지보다 조건으로 실제 데이터를 얼마나 줄일 수 있는지가 중요하다.

### 인덱스가 비효과적인 경우

- 조건을 적용해도 전체 데이터의 대부분이 남으면 인덱스 효과가 작을 수 있다.
- 작은 테이블은 전체 스캔 자체가 충분히 빠를 수 있다.
- 쓰기 작업이 매우 빈번하면 인덱스 갱신 비용이 조회 이득보다 커질 수 있다.
- 인덱스가 존재해도 옵티마이저는 비용에 따라 `Seq Scan`을 선택할 수 있다.

### WHERE절과 인덱스

- 일반 인덱스는 인덱스 컬럼의 원래 값을 기준으로 구성된다.
- `WHERE`절에서 인덱스 컬럼을 그대로 비교할 때 활용하기 좋다.
- 인덱스 컬럼에 함수나 연산을 적용하면 기존 인덱스를 효율적으로 활용하지 못할 수 있다.
- 복합 인덱스는 컬럼의 순서가 중요하며 앞쪽 컬럼에 조건이 있을수록 범위를 줄이기 좋다.

### 인덱스 추가 판단

- 카디널리티, 선택도, 테이블 규모, 조회 빈도를 확인한다.
- 조회 성능 개선과 쓰기·저장 비용의 Trade-off를 비교한다.
- 인덱스 생성 후에는 실행계획을 확인하여 실제 효과를 검증한다.

## 한 문장 정리

> 인덱스는 카디널리티가 높고 선택도가 낮은 대규모·빈번한 조회에서 효과적이며, 테이블 규모와 쓰기 비용, 조건 작성 방식까지 함께 고려해 추가 여부를 판단해야 한다.
