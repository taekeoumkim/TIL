## 1. 데이터 타입

### 데이터 타입이란?

데이터 타입(Data Type)은 테이블의 각 **Column에 저장될 수 있는 데이터의
종류**를 정의한다.

단순히 데이터의 종류를 표시하는 것이 아니라, 잘못된 형식의 데이터가
저장되는 것을 방지하는 규칙의 역할도 한다.

예를 들어 `user_id`를 `INT`로 정의했다면 숫자로 해석할 수 없는 `"회원A"`
같은 값을 저장하려 할 때 오류가 발생한다.

``` sql
CREATE TABLE users (
    user_id INT,
    name VARCHAR(50),
    join_date DATE,
    point DECIMAL(10, 2),
    marketing_agree BOOLEAN
);
```

### 주요 데이터 타입

  타입              의미                          예시
  ----------------- ----------------------------- -----------------------
  `INT`             정수형 숫자                   나이 `25`, 수량 `100`
  `VARCHAR(n)`      최대 n자의 가변 길이 문자열   이름, 이메일
  `DATE`            날짜                          `2024-01-01`
  `DECIMAL(p, s)`   소수점을 포함한 숫자          `29900.50`
  `BOOLEAN`         참/거짓                       `true`, `false`
  `TEXT`            긴 문자열                     게시글 본문

### VARCHAR와 TEXT

-   `VARCHAR(n)`은 최대 길이를 명확하게 제한할 수 있으므로 이름, 이메일,
    휴대폰 번호처럼 길이를 어느 정도 예측할 수 있는 값에 적합하다.
-   `TEXT`는 별도의 길이 제한이 필요하지 않은 긴 텍스트를 저장할 때
    사용할 수 있다.
-   결국 컬럼의 데이터 특성에 맞는 타입을 선택하는 것이 중요하다.

## 2. 스키마(Schema)

### 스키마란?

스키마(Schema)는 데이터베이스의 **구조와 제약 조건을 정의한
설계도**이다.

건물을 만들기 전에 설계도를 작성하는 것처럼, 데이터베이스를 만들기 전에
어떤 테이블과 컬럼을 만들고 어떤 데이터 타입과 제약 조건을 적용할지
정의한다.

스키마에는 다음과 같은 정보가 포함된다.

-   Table
-   Column
-   Data Type
-   Constraint

예를 들어 회원 테이블의 스키마를 다음과 같이 정의할 수 있다.

``` sql
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL UNIQUE,
    created_at DATE NOT NULL
);
```

여기서 단순히 컬럼의 이름만 정의한 것이 아니라 각 컬럼이 지켜야 할
규칙까지 함께 정의하고 있다.

### 스키마가 필요한 이유

스키마를 미리 정의하면 데이터가 일정한 구조와 규칙을 유지할 수 있다.

예를 들어 `username`에 `NOT NULL`을 적용하면 회원 이름이 없는 데이터를
저장할 수 없다.

``` sql
INSERT INTO users (
    user_id,
    username,
    email,
    created_at
)
VALUES (
    2,
    NULL,
    'jihyun@example.com',
    '2026-08-02'
);
```

위와 같은 데이터는 `username NOT NULL` 규칙을 위반하므로 저장되지
않는다.

## 3. PK와 FK

## PK (Primary Key)

PK(기본키)는 테이블 내에서 각 **Row를 유일하게 식별하는 Column**이다.

PK의 핵심 규칙은 다음과 같다.

1.  중복될 수 없다.
2.  `NULL`이 될 수 없다.

예를 들어 회원 테이블에서 `user_id`가 각 회원을 구분한다면 `user_id`가
PK가 된다.

``` text
users

user_id | name
--------+------
1       | 김민수
2       | 이지현
3       | 박서준
```

### 복합키

PK는 테이블에서 하나만 존재하지만, 반드시 하나의 컬럼으로만 구성되는
것은 아니다.

여러 컬럼을 조합하여 하나의 PK를 구성할 수도 있으며 이를
**복합키(Composite Key)**라고 한다.

예를 들어 수강 신청 테이블에서 `(학생 ID, 강의 ID)`를 조합하여 하나의
식별자로 사용할 수 있다.

------------------------------------------------------------------------

## FK (Foreign Key)

FK(외래키)는 **다른 테이블의 PK를 참조하는 Column**이다.

FK를 사용하면 서로 다른 테이블 사이에 관계를 만들 수 있다.

예를 들어 회원과 주문을 분리하면 다음과 같이 구성할 수 있다.

``` text
users

user_id | name
--------+------
1       | 김민수
2       | 이지현
3       | 박서준
```

``` text
orders

order_id | user_id | product_name
---------+---------+-------------
101      | 1       | 노트북
102      | 2       | 키보드
103      | 1       | 마우스
```

이때:

-   `users.user_id` → PK
-   `orders.order_id` → PK
-   `orders.user_id` → FK

`orders.user_id = 1`이라면 `users` 테이블에서 `user_id = 1`인 회원을
찾아 해당 주문이 김민수 회원의 주문임을 알 수 있다.

### PK와 FK의 관계

``` text
users
  │
  │ user_id
  ▼
orders.user_id
```

PK가 데이터를 유일하게 식별하는 역할이라면, FK는 **테이블과 테이블을
연결하는 역할**을 한다.

또한 하나의 테이블에는 여러 개의 FK가 존재할 수 있다.

## 4. 데이터 무결성

### 데이터 무결성이란?

데이터 무결성(Data Integrity)은 데이터가 **정확하고 일관된 상태를
유지하는 것**을 의미한다.

잘못된 데이터나 서로 모순되는 데이터가 저장되면 데이터의 신뢰성이
떨어진다.

예를 들어 다음과 같은 데이터는 문제가 있다.

``` text
customer_id | customer_name | age
------------+---------------+----
1           | 김민수        | 25
2           | 이지수        | 30
2           | 박서준        | -10
```

문제점:

-   `customer_id = 2`가 중복되어 고객을 고유하게 구분할 수 없다.
-   나이가 `-10`으로 저장되어 현실적으로 올바르지 않은 값이다.

이런 문제를 방지하기 위해 데이터베이스에서는 여러
**제약조건(Constraint)**을 사용한다.

  -----------------------------------------------------------------------
  제약조건                역할                    예시
  ----------------------- ----------------------- -----------------------
  `PRIMARY KEY`           각 행을 고유하게 식별   고객 ID

  `NOT NULL`              값이 비어 있는 것을     고객 이름
                          방지                    

  `UNIQUE`                값의 중복을 방지        이메일

  `FOREIGN KEY`           테이블 간 관계의 일관성 존재하는 고객만 주문
                          유지                    가능

  `CHECK`                 특정 조건을 만족하도록  나이는 0 이상
                          제한                    
  -----------------------------------------------------------------------

즉, 제약조건은 데이터가 이상한 상태가 되는 것을 데이터베이스 수준에서
막아주는 역할을 한다.

------------------------------------------------------------------------

## 5. 참조 무결성

### 참조 무결성이란?

참조 무결성(Referential Integrity)은 **FK가 참조하는 값이 반드시 참조
대상 테이블에 존재해야 한다는 규칙**이다.

예를 들어 상품 테이블이 다음과 같다고 하자.

``` text
products

product_id | product_name
-----------+-------------
1          | 노트북
2          | 키보드
3          | 마우스
```

주문 테이블에서 `product_id`가 `products.product_id`를 FK로 참조하도록
만들 수 있다.

``` sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    product_id INT,
    FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);
```

존재하는 상품인 `product_id = 2`를 주문하면 정상적으로 저장된다.

``` sql
INSERT INTO orders (
    order_id,
    product_id
)
VALUES (
    101,
    2
);
```

반대로 상품 테이블에 존재하지 않는 `product_id = 999`를 저장하려 하면 FK
제약조건을 위반하여 저장되지 않는다.

``` sql
INSERT INTO orders (
    order_id,
    product_id
)
VALUES (
    102,
    999
);
```

### 참조 무결성이 중요한 이유

참조 대상이 없는 데이터를 허용하면 **고아 데이터**가 생길 수 있다.

예를 들어 회원 테이블에 `user_id = 5`인 회원이 없는데 주문 테이블에
`user_id = 5`인 주문이 존재한다면, 해당 주문이 누구의 주문인지 연결할 수
없다.

참조 무결성은 이런 잘못된 관계가 만들어지는 것을 막는다.

또한 기본적으로 FK로 참조되고 있는 행은 삭제할 수 없도록 동작한다. 다만
FK 설정에 따라 다음과 같은 옵션을 사용할 수 있다.

-   `ON DELETE CASCADE`
-   `ON DELETE SET NULL`

## 6. 데이터베이스 정규화

이번 학습 자료에서는 정규화를 **주문 테이블에서 반복되는 고객 정보를
분리하는 것**이라는 관점에서 학습 목표와 목차에 포함하고 있다.

정규화의 핵심은 데이터가 불필요하게 반복되면서 생길 수 있는 문제를
줄이고, 데이터를 적절한 단위로 분리하여 관리하는 것이다.

예를 들어 하나의 주문 테이블에 주문 정보와 고객 정보를 모두 반복해서
저장한다면 같은 고객 정보가 여러 주문에서 반복될 수 있다.

``` text
orders

order_id | user_id | username | email              | product
---------+---------+----------+--------------------+--------
101      | 1       | 김민수   | minsu@example.com  | 노트북
102      | 1       | 김민수   | minsu@example.com  | 마우스
103      | 2       | 이지현   | jihyun@example.com | 키보드
```

이를 회원 정보와 주문 정보로 나누면 중복되는 고객 정보를 줄이고 각각의
데이터에 맞는 테이블로 관리할 수 있다.

``` text
users

user_id | username | email
--------+----------+-------------------
1       | 김민수   | minsu@example.com
2       | 이지현   | jihyun@example.com
```

``` text
orders

order_id | user_id | product
---------+---------+--------
101      | 1       | 노트북
102      | 1       | 마우스
103      | 2       | 키보드
```

그리고 `orders.user_id`를 `users.user_id`에 대한 FK로 연결하면 된다.

> 이번 학습 자료에서는 1NF\~3NF에 대한 상세 정의와 단계별 분해 예시는
> 본문에서 확인되지 않았으므로, 여기서는 정규화의 학습 목표인 **반복되는
> 고객 정보의 분리** 수준으로 정리한다.

## 7. 오늘 배운 내용 정리

### 데이터 타입

데이터의 성격에 맞는 타입을 지정하면 잘못된 형식의 데이터가 저장되는
것을 방지할 수 있다.

### 스키마

스키마는 데이터베이스의 구조와 제약 조건을 정의한 설계도다.

### PK

PK는 테이블의 각 Row를 유일하게 식별한다.

-   중복 불가
-   `NULL` 불가

### FK

FK는 다른 테이블의 PK 등을 참조하여 테이블 사이의 관계를 만든다.

### 데이터 무결성

데이터가 정확하고 일관된 상태를 유지하도록 하는 개념이다.

### 참조 무결성

FK가 참조하는 값이 실제 참조 대상에 존재하도록 보장한다.

### 정규화

반복되는 데이터를 적절히 분리하여 관리하는 개념으로 이해했다.

## 마무리

오늘 학습을 통해 데이터베이스는 단순히 데이터를 저장하는 공간이 아니라,
**데이터 타입과 스키마, 제약조건, PK/FK 등의 규칙을 통해 잘못된 데이터와
깨진 관계를 방지하는 구조**라는 점을 이해했다.

특히 `PK → FK → 참조 무결성`의 관계를 하나의 흐름으로 이해하는 것이
중요했다.

``` text
PK
↓
Row를 유일하게 식별
↓
FK가 다른 테이블의 PK를 참조
↓
테이블 간 관계 형성
↓
참조 무결성으로 관계가 깨지는 것을 방지
```

다음에 데이터베이스를 설계할 때는 단순히 "어떤 데이터를 저장할
것인가"뿐만 아니라 **어떤 타입으로 저장하고, 어떤 제약조건을 적용하며,
테이블을 어떻게 분리하고 연결할 것인가**까지 함께 생각해야 한다.
